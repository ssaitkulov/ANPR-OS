# AGENTS.md — правила работы ИИ-агентов в ANPR OS Fayz

Единый источник правил поведения агентов (Codex, Claude Code и другие агенты,
читающие инструкции проекта). Других копий этих правил в репозитории нет:
если правило нужно уточнить — правьте этот файл, а не его дубль.

Принципы, на которых файл построен: **Ponytail** (reuse-first, YAGNI, минимальный
достаточный код, без лишних зависимостей) и **Karpathy Guidelines**
(Think Before Coding, Simplicity First, Surgical Changes, Goal-Driven Execution).

## 0. Карта документации — куда что искать

| Файл | Что в нём | Когда открывать |
|---|---|---|
| `AGENTS.md` | эти правила | всегда |
| [`docs/CODEMAP.md`](docs/CODEMAP.md) | карта модулей, функций, связей и тестов | **до** чтения кода — сначала карта, потом исходник |
| `README.md` | установка, запуск, пользовательские возможности, состав репозитория | правка пользовательского поведения |
| `PROJECT_CONTEXT.md` | контекст, решения, хроника этапов, «почему так» (локальный файл, в Git не входит) | непонятно, зачем так сделано |
| `docs/MAINTENANCE.md` | эксплуатационные регламенты (прошивка, ротация, бэкап) | работа с живой системой |
| `docs/ACCEPTANCE.md` | приёмочный чек-лист перед боевым режимом | приёмка в бой |
| `docs/TESTING.md` | классификация тестов (UNIT/INTEGRATION/ACCEPTANCE), что запускать при каком изменении | выбор прогона |

Правила не дублируются: подробности — в файле по теме, здесь — ссылка.
Если карта (`docs/CODEMAP.md`) разошлась с кодом — **правды в коде**: сначала
проверь исходник, потом исправь карту (раздел 6).

Контекст проекта, коротко: Windows-приложение, Python 3.11–3.14, сбор проездов
с Dahua ANPR-камеры → SQLite (`data/anpr.sqlite3` — источник истины) → Telegram.
Локальный HTTP-сервис `127.0.0.1:18749`, однооконный интерфейс на CustomTkinter.

## 1. Перед правкой (Think Before Coding)

1. **Прочитай задачу и код, которого она касается.** Начни с `docs/CODEMAP.md`,
   затем открой нужный модуль. Не исследуй проект целиком.
2. **Определи область влияния и запиши её** (кратко, в ответе агенту):
   - какие файлы меняются;
   - кто вызывает меняемые функции (`grep` по вызывающим сторонам);
   - что может сломаться у пользователя: данные, которые потеряются или утекут;
     вызывающие, которые перестанут работать;
   - какие тесты это покрывают.
3. **Выскажи допущения явно.** Если задача допускает два прочтения — назови
   оба и выбери или спроси. Если чего-то не хватает — скажи и остановись,
   а не додумывай.
4. **Если есть более простой путь — скажи об этом** и предложи его.
5. **Составь короткий план с проверками** (формат: `шаг → чем проверяется`).
   Без проверяемых критериев задача не выполнена.

Правка бизнес-логики без явной просьбы пользователя — не входит в задачу.

## 2. Наименьшее достаточное изменение (reuse-first, YAGNI)

Бери **первый** вариант, который полностью решает задачу:

1. **А нужно ли это вообще?** Не делай функции, опции и «гибкость» сверх задачи;
   невыполненное назови одной строкой.
2. **Уже есть в проекте?** Используй существующий helper, виджет, сервис, паттерн
   — так, как это уже сделано рядом.
3. **Стандартная библиотека или возможности платформы?** Да, если в проекте нет
   своей реализации.
4. **Уже установленная зависимость?** Да. Никогда не добавляй зависимость ради
   нескольких строк.
5. **Одна строка, читаемая с ходу?** Одна строка.
6. Иначе — минимальный код, который работает.

Правила:

- Ленив к решению, но не к самой правке: доделай всё, что правка ломает —
  вызывающие, тесты, фикстуры, конфиг, документацию.
- Никаких «на будущее»: абстракций, обёрток, конвертаций типов, опций,
  которые никто не просил. Удаление лучше добавления.
- Сохраняй структуру проекта: слои `core / services / storage / ui`, существующие
  интерфейсы и соглашения.
- Комментарий — только там, где код не может показать «почему», одной строкой.
- Из перемещённого/объединённого кода не выбрасывай обработку ошибок и валидацию.
- Из двух равных по размеру вариантов бери тот, что корректен на краях.
- Известное ограничение помечай так: `shortcut: <ограничение>, <когда заменить>`.

## 3. Хирургические изменения (Surgical Changes)

- Меняй только то, что нужно. Не улучшай соседний код, комментарии и форматирование.
- Не рефактори то, что не сломано. Стиль — как в окружающем коде, даже если ты
  сделал бы иначе.
- Удали только те импорты, переменные и функции, которые **твоя** правка сделала
  неиспользуемыми. Чужой мёртвый код — упомяни, не удаляй.
- Каждая изменённая строка должна быть связана с задачей пользователя.
- Ошибку чини в корне: найди всех вызывающих (`grep`), исправь один раз в общем коде.

## 4. Проверка (Goal-Driven Execution)

Задача — это проверяемая цель, а не «чтобы работало».

- **Минимальный достаточный набор тестов.** Сначала точечный прогон того, что
  затронуто; полный прогон — когда правка существенная (см. шпаргалку ниже).
- **Тест на каждое нетривиальное новое поведение:** ветка, цикл, парсер,
  логика доставки, безопасность. Тривиальная правка теста не требует.
- **Новые тесты — только если без них теряется регрессионное покрытие
  критичной логики.** Не плоди тесты ради числа и не дублируй чужие.
- **Быстрые команды:**
  ```bash
  python -m pytest tests/test_<файл>.py -q        # точечно (pytest ждёт пути, не имена модулей)
  python -m unittest tests.test_stream_latency tests.test_setup_anpr   # быстрый smoke
  python -m unittest discover                     # полный набор (131 с)
  python -m pytest -q                             # тот же набор другим раннером
  python scripts/check_docs.py                    # правки только в документации
  python scripts/test_select.py --staged          # какие тесты запускать для текущего индекса
  ```
- Что запускать при каком изменении — таблица в [`docs/TESTING.md`](docs/TESTING.md);
  там же классификация UNIT/INTEGRATION/ACCEPTANCE и известные дубли проверок.
- **Полный набор** (`python -m unittest discover`) — при существенных изменениях:
  правка ядра сбора, `storage`, `services`, изоляции тестов, безопасности,
  миграций данных; перед релизом. Перед коммитом хук `.githooks/pre-commit`
  запускает тесты затронутой области (по файлам индекса) — полный набор
  он не гоняет.
- **Правки только в документации** (`*.md`, `.gitignore`) — полный прогон **не
  нужен**: достаточно `python scripts/check_docs.py` (ссылки, упомянутые файлы,
  обязательные разделы). Полный набор — только если правка документации
  меняет поведение кода или тестов.
- **Перед релизом дополнительно:** `python scripts/check_lock.py`,
  `python scripts/verify_state.py`, `python scripts/acceptance_check.py`
  и чек-лист [`docs/ACCEPTANCE.md`](docs/ACCEPTANCE.md).
- Прогон должен быть зелёным. Упавший тест — не «известная проблема», а
  недоделанная задача: почини или честно скажи, что не сделано и почему.
- Починил ошибку — сначала тест, который её воспроизводит, потом правка.

## 5. Что нельзя ослаблять

Никогда не упрощай за счёт:

- **Безопасности.** Токен управления (`X-Avrika-Control-Token`, файл
  `data/runtime/service.token`), ACL на токене, проверка источника процесса.
- **Защиты данных.** Маскирование секретов в журналах (`app/services/audit.py`),
  редиректы `token`/`password`/`secret`, отсутствие `.env` и рабочих данных в Git.
- **Обработки ошибок.** Ошибка не должна превращаться в молчаливую потерю данных:
  падение в журнал, а не в `pass`.
- **Изоляции тестового окружения.** `app/core/safe_mode.py` уводит рабочие данные
  во временный каталог и блокирует сеть, процессы и потоки. Не отключай его,
  не ослабляй заглушки сети и проверки в `tests/test_safe_mode.py`.
- **Корректности ключей и дедупликации.** `event_key` в
  `app/storage/database.py` — источник истины для уникальности проезда.

Обход этих правил допустим только по явной просьбе человека — и тогда это
отмечается в ответе.

## 6. Документация

- Обновляй документацию **только при содержательных изменениях**. Переименование
  переменной, перестановка блоков, рефакторинг без изменения поведения — правки
  в документации не требуют.
- Куда писать — по теме, без дублей:
  | Изменение | Файл |
  |---|---|
  | Пользовательское поведение, запуск, состав репозитория | `README.md` |
  | Решение, контекст, хроника этапа, «почему так» | `PROJECT_CONTEXT.md` |
  | Регламент обслуживания, процедура, откат | `docs/MAINTENANCE.md` |
  | Приёмочный чек-лист боевого режима | `docs/ACCEPTANCE.md` |
  | Модули, функции, связи, тесты | `docs/CODEMAP.md` |
- Одно правило — одно место. Не пересказывай содержимое `AGENTS.md` в README,
  не дублируй описания модулей между `README.md` и `docs/CODEMAP.md`: README —
  словами пользователя, карта — для навигации по коду.
- Если код разошёлся с документацией — исправь документацию по факту кода.

## 7. Зависимости, плагины, хуки

- Не устанавливай сторонние плагины, MCP-серверы, хуки и дополнительные
  зависимости без необходимости. Сторонняя зависимость — это долг: обновление,
  уязвимости, расхождение версий в `requirements*.txt` и `pyproject.toml`.
- Перед добавлением зависимости: есть ли это в стандартной библиотеке, в уже
  установленных пакетах, в самом проекте?
- Версии зависимостей зафиксированы в трёх файлах (`requirements.txt`,
  `requirements-lock.txt`, `pyproject.toml`) — меняешь одну, меняй все три и
  проверяй `python scripts/check_lock.py`.
- Для разработки достаточно `pytest` (в extras `dev`). Новые инструменты в
  репозиторий не кладутся без нужды.

## 8. Шпаргалка команд

```bash
# точечные тесты
python -m pytest tests/test_safe_mode.py -q
python -m unittest tests.test_outbox_reliability -v

# полный набор (CI .github/workflows/ci.yml и хук .githooks/pre-commit)
python -m unittest discover -v        # или python -m pytest -q

# согласованность зависимостей
python scripts/check_lock.py

# сверка источников данных (JSON-зеркало ↔ SQLite), код 1 при расхождениях
python scripts/verify_state.py

# автоматическая часть приёмки в бой, код 0 — замечаний нет
python scripts/acceptance_check.py
```

Запуск сервиса: `python app.py` (HTTP `127.0.0.1:18749`), панель — `run.bat`,
настройки — `settings.bat`. CLI ядра: `python anpr_telegram.py --check |
--report-now | --dry-run | --parser-test | --backfill-now`.

## 9. Как закончить задачу

В ответе агенту укажи:

1. что изменено (файлы) и почему;
2. чем проверено (точные команды и результат);
3. что **не** сделано, что не проверено и какой риск остаётся.

Правило: «лучший код — тот, которого не пришлось писать». Но «ленивый» не значит
«небрежный»: правка неполная, а её последствия не названы — это не готовая работа.
