# Приёмка перед боевым режимом

Чек-лист, по которому проверяется готовность ANPR OS Fayz к работе без присмотра.
Проверка состоит из двух частей: автоматической (по данным сервиса) и ручной
(то, что нельзя увидеть в базе: доставка сообщений, фото в мониторинге).

Автоматическая часть — `scripts/acceptance_check.py`:

```bash
python scripts/acceptance_check.py            # все проверки по сегодняшнему дню
python scripts/acceptance_check.py --day 2026-11-18
python scripts/acceptance_check.py --json     # отчёт для отчёта о приёмке
```

Код возврата: `0` — блокирующих замечаний нет, `1` — есть (`FAIL`).
`WARN` — не блокирует, но требует внимания. Выход `0` при блокирующих
замечаниях означает «в бой».

---

## 0. Подготовка

| Шаг | Команда / действие | Ожидаемый результат |
|---|---|---|
| Состояние сервиса | `curl http://127.0.0.1:18749/health` | `"status": "ok"`, камера и Telegram без ошибок |
| Согласованность зависимостей | `python scripts/check_lock.py` | версии в `requirements.txt`, `requirements-lock.txt` и `pyproject.toml` совпадают |
| Тесты | `python -m unittest discover -v` | `OK`, без падений |
| Сверка источников | `python scripts/verify_state.py` | `расхождений нет`, код 0 |
| Резервная копия | копия `.env`, `anpr.sqlite3`, `anpr_state.json`, `subscribers.json` | копия вне рабочей папки (регламент — в [MAINTENANCE.md](MAINTENANCE.md)) |
| Список получателей | `python -c "import json;print(json.load(open('subscribers.json',encoding='utf-8')))"` | все ожидаемые чаты на месте (основной чат + подписчики) |

Зафиксировать перед сутками: число подписчиков (`subscribers.json`),
идентификатор основного чата (`TELEGRAM_CHAT_ID`), свободное место на диске
(фотоархив растёт на `IMAGE_RETENTION_DAYS` дней) и текущий `last_rec_no`
(в `/status`).

## 1. 24 часа непрерывной работы

Сервис должен проработать сутки без перезапуска и без вмешательства.

| Что проверяем | Как | Ожидаемый результат |
|---|---|---|
| Сервис жив | `curl http://127.0.0.1:18749/health` | `"status": "ok"`, `started_at` не менялся |
| Камера на связи | `curl .../health` → `camera_message` | «подключено», `last_camera_data` обновляется |
| Telegram доставляет | `curl .../health` → `telegram_message` | «последнее уведомление доставлено хотя бы в один разрешённый чат» |
| Нет ошибок в журнале | `service.stderr.log` | нет строк `Traceback`, `ERROR`, `telegram_dead` |
| Очередь не растёт | `curl .../status` → `outbox.pending` | `pending = 0`, `dead = 0` |
| База растёт | `SELECT COUNT(*) FROM events` | число проездов соответствует реальным проездам дня |
| Фотоархив пишется | каталоги `images/ГГГГ-ММ-ДД/` в `IMAGE_DIR` | файлы `.jpg` появляются, старые каталоги удаляются через `IMAGE_RETENTION_DAYS` |
| Журналы ротируются | `service.stderr.log`, `.1`, `.2`, `.3` | файлы не больше `LOG_MAX_MB`, копии созданы |
| WAL не растёт | `anpr.sqlite3-wal` | размер стабилен (поток обслуживания делает `wal_checkpoint`) |
| Состояние пишется | `anpr_state.json` | обновляется, `last_rec_no` растёт |

## 2. Сверка источников после суток

```bash
python scripts/verify_state.py        # код 0 — расхождений быть не должно
python scripts/acceptance_check.py    # та же проверка плюс остальные
```

Критерий приёмки: **расхождений между JSON-зеркалом и SQLite — 0**
(`json_records` = `db_rows_in_state_days`). Любое расхождение означает потерю
или задвоение проезда: работу не принимают, разбираются по журналу.

---

## 3. Имитация обрыва камеры

**Как устроено:** живая подписка `snapManager.cgi` и добор архива
(`recordFinder.cgi`) ходят по одной и той же камере. Когда камера недоступна,
потоки камеры и добора молча ждут, а очередь доставки продолжает работать —
доставка не зависит от камеры.

1. **Отключить камеру.** Вариант для проверки без физического доступа —
   заблокировать адрес камеры на машине сервиса (PowerShell, права администратора):

   ```powershell
   New-NetFirewallRule -DisplayName "anpr-block-camera" -Direction Outbound `
     -RemoteAddress 192.168.100.249 -Action Block
   ```

2. **Дождаться 5–10 минут.** Ожидаемое поведение:
   - в `service.stderr.log` — обрыв и переподключение камеры, без падения сервиса;
   - `/health` → `camera_message` сообщает об обрыве, `status` остаётся `ok`;
   - очередь доставки продолжает развозиться (`pending` не растёт);
   - `/status` и `/entries/today` продолжают отдавать данные из базы.

3. **Снять блокировку и дождаться планового добора** (не более `BACKFILL_INTERVAL`,
   по умолчанию 60 с):

   ```powershell
   Remove-NetFirewallRule -DisplayName "anpr-block-camera"
   ```

4. **Проверить добор:**

   ```bash
   curl -X POST http://127.0.0.1:18749/backfill-now    # можно вручную, не дожидаясь цикла
   python scripts/verify_state.py
   ```

   Ожидаемый результат: проезды, пропущенные во время обрыва, появились в базе
   с признаком `backfill = 1`, в Telegram ушёл один список пропущенных проездов
   (`kind=backfill`), а в JSON-зеркале нет расхождений с SQLite.

5. **Живой проезд не должен задублироваться.** Если проезд из архива позже
   приходит live — та же строка базы обновляется, новой не создаётся:
   `SELECT COUNT(*) FROM events WHERE plate=? AND day=?` не растёт.

## 4. Имитация обрыва Telegram

**Как устроено:** очередь недоставленных живёт в SQLite. При недоступности
Telegram сообщения копятся в очереди и уходят сразу после восстановления связи —
отдельным потоком, независимо от камеры.

1. **Отключить Telegram.** Вариант через межсетевой экран (PowerShell):

   ```powershell
   $ips = (Resolve-DnsName api.telegram.org -Type A).IPAddress
   foreach ($ip in $ips) {
     New-NetFirewallRule -DisplayName "anpr-block-tg-$ip" -Direction Outbound -RemoteAddress $ip -Action Block
   }
   ```

   Альтернатива без правил брандмауэра: временно подменить `TELEGRAM_BOT_TOKEN`
   в `.env` на нерабочий и перезапустить сервис — отправки будут уходить в очередь.

2. **Дождаться 5–10 минут.** Ожидаемое поведение:
   - проезды продолжают записываться в SQLite и в фотоархив;
   - в `outbox` появляются записи `status = 'pending'`, счётчик `pending`
     растёт (`curl .../status` → `outbox`);
   - в журнале — ошибки Telegram, но **нет** `telegram_dead` (попытки должны
     не исчерпаться: `OUTBOX_MAX_ATTEMPTS = 10`, пауза растёт экспоненциально);
   - камера продолжает работать, живая подписка не падает.

3. **Вернуть связь** (снять правила, либо вернуть настоящий токен и перезапустить):

   ```powershell
   Remove-NetFirewallRule -DisplayName "anpr-block-tg-*"
   ```

   Ожидаемый результат: очередь развозится сама (интервал `OUTBOX_FLUSH_INTERVAL`,
   по умолчанию 15 с), `pending` возвращается к 0, `dead` остаётся 0, а
   повторно пришедшие сообщения не дублируются (`curl .../status` → `outbox.sent`).

4. **Живой проезд во время обрыва Telegram не потерян:** он есть в базе
   (`SELECT COUNT(*) FROM events`) и его текст ушёл из очереди.

## 5. Отчёт за день

| Шаг | Действие | Ожидаемый результат |
|---|---|---|
| Время отправки | дождаться `REPORT_TIME` (20:00) | отчёт уходит всем получателям в течение минуты |
| Отметка | `python -c "import json;print(json.load(open('anpr_state.json',encoding='utf-8'))['reported_days'])"` | сегодняшний день в списке |
| Без дублей | `POST /report-now` вручную после отчёта | отчёт отправляется повторно только по явной команде; в состоянии день не дублируется (`reported_days` без повторов) |
| Догон за вчера | выключить сервис до 20:00, включить на следующий день | отчёт за пропущенный день уходит сам (catch-up) |
| Содержимое | сообщение в Telegram | число въездов, число разных номеров, средняя скорость, список номеров и времени |
| Счётчик | `curl .../status` | `outbox.dead = 0`, в `outbox` видны отправленные отчёты (`kind=report`) |

## 6. Дашборд и фотоархив

1. Открыть мониторинг (`run.bat` → «Мониторинг» / `app/ui/dashboard.py`).
2. Выбрать период, в который попал обрыв камеры.
3. Ожидаемый результат:
   - проезды из архива видны в ленте и помечены «· Архив»;
   - метрики (въезды/выезды/разные номера/часовая гистограмма) считают и
     архивные проезды;
   - у живых проездов открывается фотография (`/passages/{id}/photo`),
     у проездов из архива — ожидаемо без фото: **камера снимки из архива не
     отдаёт** (`loadfile.cgi?action=downPicByTime` на этой камере —
     `501 Not Implemented`), фото архивного проезда может быть только уже
     сохранённый сервисом (`SAVE_PHOTOS=true`, `BACKFILL_SEND_PHOTOS=true`);
   - поиск по номеру работает по всем проездам периода.

Проверка снимков на диске:

```bash
python scripts/acceptance_check.py --skip-service   # раздел «Фотоархив за …»
```

Критерий: у всех живых проездов дня снимок существует по пути из базы
(`passage_photo_paths`); «Фотографии этих проездов недоступны» в списке добора —
не дефект, а следствие ограничения камеры.

## 7. Все получатели получили событие

1. Снять список чатов до события:

   ```bash
   python -c "import json,os;s=json.load(open('subscribers.json',encoding='utf-8'));print(len(s));print(sorted(map(str,s)))"
   ```

   Получатели = `TELEGRAM_CHAT_ID` + подписчики из `subscribers.json`,
   отфильтрованные `ALLOWED_CHAT_IDS`. Их должно быть столько же, сколько
   ожидается (например, 104, если подписчиков 104).

2. Проверить доставку события:

   - `curl http://127.0.0.1:18749/health` → `telegram_delivery`:
     `delivered` = числу получателей, `failed` = 0;
   - в журнале: `[delivery] started=... success=True` рядом с этим проездом;
   - в `outbox` нет записей `pending`/`dead` по этим чатам;
   - вручную: сообщение о въезде пришло в каждый чат (в группе — отметка
     «доставлено» под каждым участником, если включены её отметки).

3. Если `failed > 0` — у этих чатов текст лежит в очереди; он уйдёт при
   следующем проходе очереди. Не ушёл — запись станет `dead`, событие
   `telegram_dead` появится в `GET /events`.

**Решение о приёмке:** все пункты со знаком ☐ и код выхода `0` у
`scripts/acceptance_check.py` → можно в бой. Любой пункт не пройден — работа
продолжается, причина фиксируется в журнале, пункт проверяется заново.
