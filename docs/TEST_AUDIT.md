# Аудит тестов ANPR OS Fayz

Разовый аналитический отчёт: что в наборе тестов дублируется, чего в нём не
хватает и что с этим делать. **Код приложения и файлы тестов в ходе аудита не
менялись** — правились только измерительные инструменты (замер покрытия) и
появился этот файл.

Правила работы агентов — в [`AGENTS.md`](../AGENTS.md), карта кода — в
[`CODEMAP.md`](CODEMAP.md), классификация набора и таблица «что запускать» —
в [`TESTING.md`](TESTING.md). Этот отчёт **не переопределяет** `TESTING.md`:
правила набора живут там, здесь — факты, измерения и план. Итог аудита
(правка `TESTING.md` §2 и §4, `CODEMAP.md` §7, изменение состава тестов) —
отдельная задача, как и предписывает сам `TESTING.md` §6.

## 0. Как измеряли

| Что | Как | Результат |
|---|---|---|
| Состав набора | `python -m pytest --collect-only -q` | **373 теста** в 32 файлах |
| Время полного прогона | `python -m unittest discover` / `python -m pytest -q` | **177 с** / **179 с** (замерено на этой машине) |
| Покрытие кода | `coverage run --source=app -m pytest -q` | **74 %** (6377 операторов, 1652 не покрыто) |
| Дубли по поведению | чтение тел тестов + попарное сравнение (`difflib`) | **≈40 пар** (12 из них — с одинаковыми именами) |
| Пробелы | карта непокрытых строк по каждому модулю | **14 пробелов**, 7 — в критичной логике |

Покрытие снято под pytest; под `unittest discover` ветки `detect_test_run()` и
`_flag_value()` выполняются, а под pytest — нет (`conftest.py` включает режим
явно). На выводы это не влияет, кроме оговорённого в пробеле №8.

### 3.3 Дублирующая обвязка (код, а не тесты)

`test_context_panel.py` и `test_service_panel.py` (526 и 573 строки) содержат
**почти идентичную оснастку**: словарь `HEALTH`, `EMPTY_DASHBOARD`, объект
`FAKE_SERVICE`, класс `FakeCapture`, базовый класс `ShellTestCase` с
одинаковыми `setUp`/`tearDown`/`pump`/`click` — **51 совпадающая строка в
шапке и 62 из 76 строк базового класса**. Это ~200 строк копипасты, которая
расходится при любой правке.

Действие: вынести общую оснастку в `tests/anpr_testenv.py` (там уже лежит
`IsolatedTestCase`) и импортировать её в оба файла.

> **Важно:** в момент аудита эти два файла (а также `test_stage2_ui.py`)
> правит другой агент (рефакторинг шапки и контекстной панели). Пункты 3.2 и
> 3.3 по этим файлам применять **после** мержа его работы, иначе конфликт.

## 7. Вывод про CI

**Оставить один раннер: `pytest`.** Убрать из `.github/workflows/ci.yml` шаг
`python -m unittest discover -v`.

Почему именно pytest:

1. **Разный teardown.** `tests/conftest.py` после **каждого** теста ждёт
   фоновые потоки (`join_threads`) и в конце сессии снимает защитные подмены
   (`finalize`). Под `unittest discover` `conftest.py` не загружается: потоки
   ждут только в `atexit`, а между тестами живут.
2. **Безопасность важнее чистого состояния.** `safe_mode.finalize()` снимает
   подмены **только** если все потоки завершились; при pytest это проверяется
   после каждого теста и на границе сессии.
3. **Диагностика.** pytest даёт нормальный traceback с источником, а
   `unittest discover` — список `FAIL:` без указания строки в контексте.
4. **Экономия.** Измеряно: 179 с против 177 с — набор один и тот же, второй
   прогон не добавляет ничего. В матрице 3.11–3.14 это **8 полных прогонов
   ≈ 24 минуты** вместо 4.
5. **pytest уже стоит** в CI (`python -m pip install pytest`) — дополнительных
   зависимостей не появляется.

`unittest discover` оставить в `.githooks/pre-commit` — только как запасной
вариант для машины без pytest. Но раннер в хуке стоит привести к тому же,
что в CI: если локально гоняется `unittest`, а в CI — `pytest`, то тест может
проходить локально и падать в CI (разный teardown). Практичный вариант
хука: `python -m pytest -q`, если pytest установлен, иначе
`python -m unittest discover`; для коммитов только с правкой `*.md` — быстрый
smoke (`tests.test_stream_latency tests.test_setup_anpr`, 0,3 с), полный прогон
оставить на CI.
