# Обслуживание ANPR OS Fayz

Регламенты для обслуживающего персонала: обновление прошивки камеры, замена камеры,
ротация фотографий, резервное копирование и обновление зависимостей.

Все действия выполняются на компьютере, где установлена программа.
Сервис слушает только `127.0.0.1:18749` — наружу ничего не отдаётся.

---

## 1. Обновление прошивки камеры (Dahua ITC413)

### 1.1. До

1. Остановите сбор: окно управления → «Остановить сбор» (или закройте `run.bat`).
2. Сделайте резервную копию текущих настроек камеры:
   веб-интерфейс камеры → `Настройки` → `Система` → `Настройки переноса` → «Экспорт в локальный файл»
   (файл `.bin` сохраните рядом с программой в папку `backup/`).
3. Запишите в журнал обслуживания: модель, IMEI/серийный номер, текущую версию прошивки
   (веб-интерфейс → `Настройки` → `Система` → `Сведения о версии`).

### 1.2. Прошивка

1. Скачайте прошивку только с официального сайта Dahua и проверьте контрольную сумму из файла
   ` Dahua-ITC413-Firmware-*.MD5` (приложение его не проверяет — это делает человек).
2. Веб-интерфейс → `Настройки` → `Система` → `Обновление` → «Обновить локально» → выберите файл.
3. Не выключайте камеру во время прошивки. Камера перезагрузится — это нормально, связь пропадёт на 3–10 минут.

### 1.3. После прошивки — обязательная проверка

| Что проверить | Как | Ожидаемо |
|---|---|---|
| Камера отвечает | `http://127.0.0.1:18749/health` | `"status": "ok"`, `camera` = адрес камеры |
| События проездов идут | окно мониторинга, один реальный проезд | 2 фото (сцена + номер) в Telegram |
| Время камеры | веб-интерфейс → `Настройки` → `Система` → `Общие` → «Настройка времени» | NTP включён, смещение ≤ 1 с |
| Полосы и направление | `Настройки` → `Дорожное` → `Пересечение` → Полоса 1–4 | `JunctionDirection` 0 = въезд, 1 = выезд |
| Детектор номера | `Настройки` → `Дорожное` → `Пересечение` → «Распознавание номера» | Включено, страна/цвет по умолчанию — любые |
| Архив | `POST http://127.0.0.1:18749/backfill-now`, затем журнал | `service.stderr.log`: `[backfill] пропущенных нет` |

Если после прошивки изменилось поле направления (`JunctionDirection`), обновите `DIRECTION` в `.env`:
пусто — оба направления, `Approach` — только въезд, `Leave` — только выезд.

Если события перестали приходить, а в `/health` камера видна — проверьте, что в веб-интерфейсе
не отключили событие `TrafficJunction` и не сменили канал (`DAHUA_CHANNEL`).

### 1.4. Откат

Восстановите сохранённый `.bin` через `Настройки` → `Система` → `Обновление` → «Обновить локально»
либо верните заводские настройки и заново внесите параметры из раздела 1.3.
После отката снова прогоните проверку 1.3.

## 2. Замена камеры (другая модель или другой адрес)

### 2.1. Подготовка

1. Остановите сбор.
2. Сделайте резервную копию `.env` и `anpr.sqlite3` (раздел 5).
3. Если новая камера в другой сети или с другим портом — измените в `.env`:

```ini
DAHUA_HOST=192.168.100.250
DAHUA_PORT=80
DAHUA_USERNAME=admin
DAHUA_PASSWORD=<пароль>
DAHUA_CHANNEL=1        # 0 для первой камеры, 1 для второй
CAMERA_NAME=Ворота 2
IMAGE_DIR=images-v2     # отдельная папка фотографий для новой камеры
```

4. В окне «Настройки» (`settings.bat`) укажите новый адрес и пароль — окно само перезапишет
   `DAHUA_HOST`/`DAHUA_PORT` в `.env`.

### 2.2. Разделение данных между камерами

Обе камеры ведут одну базу `anpr.sqlite3` (источник истины по проездам), поэтому:

- `CAMERA_NAME` в `.env` добавляется в подпись сообщения — по нему видно, с какой камеры проезд;
- если камеры стоят на разных объектах и данные не должны смешиваться — заведите отдельную копию
  каталога программы и отдельный `IMAGE_DIR`/`.env` для второй камеры;
- при переносе на новый `IMAGE_DIR` старые фотографии остаются в прежней папке, ссылки в базе
  (`passage_photo_paths`) продолжают работать, пока файлы на месте.

### 2.3. Проверка после замены

1. Запустите `run.bat`, откройте `http://127.0.0.1:18749/health` — `camera` должен совпадать с новым адресом.
2. Проведите один реальный проезд: в Telegram приходят два фото и подпись с новым `CAMERA_NAME`.
3. `GET http://127.0.0.1:18749/entries/today` — проезд виден в списке.
4. `POST http://127.0.0.1:18749/backfill-now` — архив новой камеры читается, ошибок в `service.stderr.log` нет.
5. Проверьте, что номер из `DIRECTION`/полосы определился верно: `Object.Lane` и `JunctionDirection`
   в подписи события из `service.stderr.log` (`DEBUG_RAW=true` даёт сырой JSON события).

## 3. Ротация фотографий в `images/`

Фотографии — производные данные: восстанавливаются только до момента, пока камера хранит архив.
Долговременный архив — `anpr.sqlite3` (текст, номера, время, пути к фото).

### 3.1. Политика хранения

| Каталог | Срок хранения | Как чистится |
|---|---|---|
| `images/ГГГГ-ММ-ДД/` | 30 дней | вручную или задачей Планировщика |
| `images/diagnostic/` | нет | диагностические снимки удаляются сразу после проверки |
| `anpr.sqlite3` | бессрочно | вручную, отдельной резервной копией |

### 3.2. Процедура (вручную)

1. Остановите сбор — на момент копирования файлы не должны дописываться.
2. Убедитесь, что в базе нет проездов старше срока хранения без фото:
   ```powershell
   python -c "import sqlite3;c=sqlite3.connect('anpr.sqlite3');print(c.execute('select count(*) from events').fetchone())"
   ```
3. Удалите каталоги старше 30 дней:
   ```powershell
   Get-ChildItem images -Directory |
     Where-Object { $_.Name -match '^\d{4}-\d{2}-\d{2}$' -and (Get-Date) - [datetime]::Parse($_.Name) -gt (Get-Date).AddDays(-30) } |
     Remove-Item -Recurse -Force
   ```
4. Запустите сбор и убедитесь, что мониторинг показывает фото (фото свежих проездов на месте).
   Удалённые файлы в `passage_photo_paths` остаются ссылками на несуществующий файл — эндпоинт
   `/passages/{id}/photo` в этом случае отвечает 404, остальные данные проезда целы.

### 3.3. Процедура (автоматически, Планировщик Windows)

Создайте задачу «Evrika: ротация photos»:
- Триггер: ежедневно в 03:00.
- Действие: `powershell.exe -NoProfile -ExecutionPolicy Bypass -File "%USERPROFILE%..\..\..\...\rotate_images.ps1"` —
  или вставьте команду из 3.2 в поле «Аргументы».
- Условие «Запускать только при питании от сети» — обязательно.

Альтернатива без Планировщика: `python -c "import shutil,pathlib,datetime;..."` — тот же принцип,
запускать от имени того же пользователя, от которого работает сервис.

## 4. Журналы

| Файл | Что внутри |
|---|---|
| `service.stderr.log` | ошибки камеры, Telegram, backfill, доставки очереди |
| `service.stdout.log` | поток событий (большой, можно ротировать по размеру) |
| `anpr_state.json` | рабочее зеркало: дедупликация, `last_rec_no`, `last_report_date` |

Ротация журналов: `service.stderr.log` и `service.stdout.log` можно удалять при остановленном сервисе.
Их размер растёт неограниченно — настройте Планировщик на очистку файлов старше 14 дней.
Текущее состояние сервиса всегда доступно по `GET /health` и `GET /events`.

## 4.1. Ключ события и сверка источников

В таблице `events` одна строка = один проезд. Ключ строки — `sha256(день|время|номер|полоса|направление)`,
то есть строится из содержимого проезда, а не из идентификаторов прошивки (`GroupID` камера переиспользует).
Идентификаторы прошивки лежат отдельно: `source_key` (`GroupID:IndexInGroup:номер:полоса`),
`group_id` (сам `GroupID`), `rec_no` (номер записи в архиве камеры).

Изменение схемы и пересчёт старых ключей выполняются при старте сервиса (`storage.py`,
миграция идемпотентная, данные не теряются). После обновления проверьте базу:

```powershell
python tools/verify_state.py
```

Скрипт сверяет JSON-зеркало (`anpr_state.json`) с SQLite и возвращает код 1, если есть расхождения
(проезд есть только в одном источнике, разошлись поля или флаг `backfill`).
Расхождений быть не должно: 0 — расхождений нет.

## 4.2. Очередь недоставленных (outbox)

Недоставленные сообщения лежат в таблице `outbox` базы `anpr.sqlite3` — одна строка = одно
сообщение для одного чата (`chat_id`). Очередь переживает рестарт сервиса.

| Статус | Что значит |
|---|---|
| `pending` | ждёт отправки; время следующей попытки — в колонке `next_attempt_at` |
| `sent` | доставлено |
| `partial` | длинное сообщение доставлено частично, хвост ждёт отдельной строки |
| `dead` | попытки исчерпаны, автоматическая доставка прекращена |

Как это работает:

1. Очередь развозит отдельный поток с интервалом `OUTBOX_FLUSH_INTERVAL` секунд (по умолчанию 15) —
   доставка не зависит от камеры. Цикл камеры делает тот же проход, но под замком, поэтому одно
   сообщение не уходит дважды.
2. Успех считается по каждому чату отдельно: чат, где отправка не удалась, получает свою запись
   очереди с его `chat_id` и докачивается отдельно.
3. Неудачная попытка сдвигает `next_attempt_at`: пауза растёт экспоненциально
   (`OUTBOX_RETRY_BASE_SECONDS`, по умолчанию 30 с: 30, 60, 120 …, потолок —
   `OUTBOX_RETRY_MAX_SECONDS`).
4. Когда число попыток превысило `OUTBOX_MAX_ATTEMPTS` (по умолчанию 10), запись становится `dead`:
   она остаётся в базе, но больше не отправляется. Факт попадает в `GET /events`
   (тип `telegram_dead`) и в stderr.

Проверка состояния очереди:

```powershell
python -c "import sqlite3;c=sqlite3.connect('anpr.sqlite3');print(c.execute('select status,count(*) from outbox group by status').fetchall())"
```

Те же счётчики видны в `GET /status` (поле `outbox`: `pending`, `sent`, `partial`, `dead`).

Если записи много попали в `dead` (например, был долгий обрыв связи или неверный токен), после
устранения причины их можно вернуть в работу одной командой:

```powershell
python -c "import sqlite3;c=sqlite3.connect('anpr.sqlite3');c.execute(\"update outbox set status='pending',attempts=0,next_attempt_at=0 where status='dead'\");c.commit()"
```

Сообщения из `dead` уходят получателям следующим проходом очереди.

## 5. Резервное копирование

1. Остановите сбор (иначе копия `anpr.sqlite3` может быть неконсистентной из-за WAL).
2. Скопируйте в `backup/ГГГГ-ММ-ДД/`:
   - `.env` — секреты камеры и бота (в открытом виде, не отправляйте наружу);
   - `anpr.sqlite3` — база проездов и очередь недоставленных;
   - `anpr_state.json` — зеркало состояния;
   - `subscribers.json` — список подписчиков.
3. `images/` в резервную копию не входит: фотографии восстанавливаются из архива камеры.
4. Храните копии на носителе вне рабочего компьютера. Проверяйте восстановление раз в квартал:
   положить `anpr.sqlite3` в чистый каталог, запустить сервис, открыть `/status`.

## 6. Обновление зависимостей

1. Проверенный набор пакетов зафиксирован в `requirements-lock.txt` (Python 3.14.7, Windows 11).
2. Обновление одного пакета: изменить версию в `requirements.txt` **и** в `requirements-lock.txt`,
   затем `python -m pip install -r requirements.txt && python -m pytest -q`.
3. Только после зелёных тестов обновлять рабочую машину.
4. Не вызывайте `pip install -U` без правки файлов: без верхних границ сборка «поедет» при
   выходе новой версии пакета (именно поэтому границы заданы в `requirements.txt` и `pyproject.toml`).
5. Ожидаемый список версий и состояние проекта — в `README.md` и `pyproject.toml`.
