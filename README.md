# Камера и Telegram

ANPR OS Fayz — сбор проездов с Dahua ANPR-камеры в Telegram, локальный сервис
и мониторинг. Каждый въезд приходит альбомом из двух снимков, в 20:00 уходит
итог дня, после обрыва камеры пропущенное добирается из архива самой камеры.
Источник истины — база `data/anpr.sqlite3`; всё остальное (JSON-зеркало, файлы
фотографий, журналы) живёт рядом и приводится к базе.

## Установка

Нужен **Python 3.11–3.14** (проверено на 3.14.7, Windows 11 x64).

```bash
git clone <репозиторий> anpr-os-fayz
cd anpr-os-fayz
python -m pip install -r requirements-lock.txt   # точный набор с транзитивными
python -m pip check
copy .env.example .env                          # Windows: copy, Linux: cp
```

Дальше — заполнить `.env` (хост камеры, логин, пароль, токен бота, чат) и
запустить `run.bat` (меню: сбор, отчёт, добор архива, проверка, сервис).
Либо вручную: `python app.py` — сервис поднимается на `127.0.0.1:18749`,
а окно приложения запускается из `run.bat`.

Для установки на **рабочий ПК без интернета** — [`docs/DEPLOY.md`](docs/DEPLOY.md):
офлайн-установка из `deploy/wheelhouse/`, проверка `scripts/verify_install.py`.

Сборка пакета (не обязательна — сервис работает прямо из папки):

```bash
python -m pip install build
python -m build            # соберёт sdist и wheel в dist/
python -m pip install dist/anpr_os_fayz-1.0.0-py3-none-any.whl
```

## Как пользоваться

Откройте **run.bat**. Откроется единое окно «Эврика», сбор запустится автоматически.
В шапке окна слева — логотип и навигация между разделами «Мониторинг» и «Настройки»,
справа — три независимых индикатора (сервис, камера, Telegram) и кнопка «Управление».
Отдельной нижней панели статуса нет: все индикаторы собраны в шапке, а управление
сервисом спрятано в раскрывающуюся панель.

- **Сервис: работает / остановлен / запускается / останавливается / перезапускается / ошибка** — состояние ANPR-сбора.
- **Камера: подключена / нет связи / подключение / неизвестно** — соединение с камерой.
- **Telegram: работает / недоступен / проверка / неизвестно** — доступность бота.
  Успешность последней отправки — отдельный диагноз, он показан в панели управления.
- Индикаторы независимы: сломанная камера не красит в красный сервис, а недоступный
  Telegram не мешает управлять сбором.
- **Управление** — раскрывающаяся панель под правой частью шапки (то же самое —
  нажатие на любой индикатор): состояние сервиса с PID, временем работы и портом,
  состояние камеры (имя, IP, приём ANPR-событий), состояние Telegram (связь,
  последняя доставка) и кнопки управления.
- **Запустить** — начать сбор. **Остановить** — прекратить сбор (требует подтверждения).
  **Перезапустить** — остановить сбор и запустить заново с сохранёнными настройками
  (тоже с подтверждением). **Журнал** — открыть журнал сервиса в блокноте.
- Панель закрывается повторным нажатием «Управление», клавишей Escape, кликом вне
  панели или при переходе в другой раздел.

Окно можно закрыть: сбор продолжится, программа останется в трее. При этом видео
приостанавливается, а ANPR-мониторинг продолжает работать. Размер и положение окна
запоминаются между запусками. После перезагрузки Windows откройте run.bat.
Автоматический запуск при включении компьютера включается переключателем «Запускать с Windows»
в окне «Настройки»: программа регистрирует себя в автозагрузке Windows (HKCU\...\Run).

## Настройки

Адрес камеры, логин, пароль, токен Telegram, ID чата и список разрешённых чатов.
Для личного использования укажите свой ID в обоих полях и напишите боту /start.
В разрешённой группе команды доступны всем участникам группы.
После сохранения откройте «Управление» в шапке окна и нажмите «Перезапустить». Вкладки настроек
(«Камера», «Telegram», «Мониторинг», «Приложение») — слева; справа форма шириной
до 800 px с кнопкой проверки подключения у камеры и бота.
Секреты находятся в локальном .env без шифрования. Не передавайте этот файл другим.

## Telegram

/start — подписаться; /stop — отписаться от подписки; /report — отчёт за сегодня.
Основной чат из настроек получает события независимо от подписки.
Направление движения и часы камеры ещё требуют проверки реальным проездом.

## Где хранятся проезды

Все рабочие данные лежат в каталоге `data/` рядом с программой:

```
data/
├── data/anpr.sqlite3        база проездов (SQLite — источник истины)
├── data/anpr_state.json     зеркало состояния
├── data/subscribers.json    список чатов-получателей
├── data/ui_preferences.json настройки панели
├── data/ui_window.json      положение и размер окна
├── photos/             фотографии проездов (data/photos/ГГГГ-ММ-ДД/*.jpg)
├── runtime/            PID-файл и токен управления
└── logs/               журналы сервиса и управления
```

Пути считаются от корня проекта (`app/core/paths.py` — единственный источник
правды), а не от текущей директории и не от адреса диска. Поэтому папку проекта
можно скопировать на другой диск целиком: ничего править не нужно, абсолютных
путей в настройках нет.

**`data/anpr.sqlite3` — единственный источник истины.** В таблице `events` одна строка = один проезд
(и live-событие, и запись из архива камеры). Ключ строки — `sha256(день|время|номер|полоса|направление)`,
то есть строится из самого проезда, поэтому повторные проезды с одним и тем же `GroupID` прошивки
не теряются. Идентификаторы прошивки хранятся отдельно и в ключ не входят:
`source_key` = `GroupID:IndexInGroup:номер:полоса`, `group_id` = сам `GroupID`,
`rec_no` = номер записи в архиве камеры (у проездов из архива). Схема и старые ключи
пересчитываются при старте — миграция идемпотентная (`app/storage/database.py`).
Фотографии лежат файлами в `data/photos/` (в базе — только пути, и пути эти
**относительные**: `ГГГГ-ММ-ДД/файл.jpg` от каталога снимков, поэтому перенос
проекта их не рвёт). Запись снимков на диск
включается настройкой `SAVE_PHOTOS` (по умолчанию `true`); выключается только осознанно,
иначе мониторинг не сможет показать фото проезда.

`data/anpr_state.json` — рабочее зеркало: окно дедупликации, отпечатки снимков, `last_rec_no`,
`last_report_date`. Проезды в нём хранятся последние `STATE_KEEP_DAYS` дней (по умолчанию 30)
и служат страховкой на случай сбоя записи в базу; при старте и раз в минуту записи
синхронизируются в базу.

Отчёт в Telegram, `/status`, `/entries/today` и мониторинг читают один и тот же SQLite.

Сверка двух источников (JSON-зеркало ↔ SQLite) — `python scripts/verify_state.py`:
печатает расхождения и возвращает код 1, если они есть.

## Локальные эндпоинты

Сервис слушает только `127.0.0.1:18749` — наружу ничего не отдаётся. Все эндпоинты читают
и пишут ту же базу `data/anpr.sqlite3`, что и мониторинг.

| Метод и путь | Что делает | Пример |
|---|---|---|
| `GET /health` | Состояние процесса, камеры и Telegram, время запуска, счётчики последней доставки (`telegram_delivery`) | `curl http://127.0.0.1:18749/health` |
| `GET /status` | Сводка за сегодня: число въездов, уникальные номера, счётчики очереди (`outbox`: pending/sent/partial/dead), подписчики, аптайм | `curl http://127.0.0.1:18749/status` |
| `GET /entries/today` | Список проездов за сегодня (время, номер, полоса, направление) | `curl http://127.0.0.1:18749/entries/today` |
| `GET /passages` | Последние проезды из базы (для ленты мониторинга) | `curl http://127.0.0.1:18749/passages` |
| `GET /passages/{id}/photo` | Фотография проезда по его id (JPEG); 404, если файла уже нет | `curl -o p.jpg http://127.0.0.1:18749/passages/12/photo` |
| `GET /events` | Журнал операционных событий (`?after=id` — только новые) | `curl "http://127.0.0.1:18749/events?after=0"` |
| `POST /report-now` | Отправить отчёт за сегодня в Telegram сейчас | `curl -X POST http://127.0.0.1:18749/report-now` |
| `POST /backfill-now` | Запустить добор архива камеры сейчас | `curl -X POST http://127.0.0.1:18749/backfill-now` |
| `POST /shutdown` | Мягко остановить сервис (потоки, состояние, база). **Требует секретный токен** | `curl -X POST -H "X-Avrika-Control-Token: $(cat data/runtime/service.token)" http://127.0.0.1:18749/shutdown` |

`/report-now` и `/backfill-now` возвращают сразу и выполняют работу в фоне:
отчёт приходит в Telegram, список архивных проездов — тем же списком, что и при плановом доборе.
`/shutdown` останавливает сервис штатно: фоновые потоки дорабатывают операцию, состояние
пишется в `data/anpr_state.json`, база закрывается, процесс завершается сам.

**Остановка защищена токеном.** Без заголовка `X-Avrika-Control-Token` с правильным значением
сервер отвечает `401` и пишет отказ в `data/logs/service.control.log`. Токен лежит в файле `data/runtime/service.token`
(создаётся при первом запуске сервиса); права на файл ограничены — доступ только у владельца,
то есть у того же локального пользователя, от имени которого работает сервис. Основание для
доступа — сам секрет, а не `localhost`, `Origin`, `Referer` или имя заголовка: панель управления
и `service_control.py` читают тот же файл, а посторонний процесс на этой машине токен не прочтёт.
В `/health` сервер объявляет версию протокола (`protocol`) и требование токена (`shutdown_auth`),
поэтому старая и новая версии панели и сервиса понимают друг друга.

## Зависимости и версии

Проверенная среда: Python 3.14.7 (Windows 11 x64).

- `requirements.txt` — прямые зависимости с **зафиксированными версиями**
  (`requests==2.32.5` и т.д.). Это рабочая сборка: обновление пакета не должно
  молча сломать боевой режим.
- `requirements-lock.txt` — полный набор проверенного окружения вместе с
  транзитивными зависимостями. Установка для новой машины:
  `python -m pip install -r requirements-lock.txt`.
- `pyproject.toml` — метаданные проекта, `requires-python = ">=3.11,<3.15"` и те же
  зафиксированные версии; `pip install .` даёт то же самое окружение.
- `python scripts/check_lock.py` — проверка, что версии в этих трёх файлах не
  разошлись (код 0 — совпадают). Запускается вручную и в CI.
- `run.bat` доустанавливает `requirements-lock.txt` сам, если чего-то не хватает —
  новая машина получает тот же проверенный набор, что и CI.

Порядок обновления зависимостей (чтобы сборка не «поехала»): править версию в
`requirements.txt`, `requirements-lock.txt` и `pyproject.toml` → `pip install -r
requirements-lock.txt` → `pip check` → `python -m unittest discover -v` → только
потом обновлять рабочую машину.

Для тестов: `python -m unittest discover -v` (полный набор) или `python -m pytest -q`
(тот же набор другим раннером); быстрая проверка без камеры —
`python -m unittest tests.test_stream_latency tests.test_setup_anpr`. CI (.github/workflows/ci.yml) гоняет
один полный прогон `python -m pytest -q` на Windows для Python 3.11, 3.12, 3.13 и 3.14 плюс быструю
проверку совместимости на стандартной библиотеке, проверяет `pip check` и то, что тесты не создали
`data/anpr.sqlite3` / `data/anpr_state.json` в рабочей папке. Что запускать при каком изменении,
классификация тестов и известные дубли — в [docs/TESTING.md](docs/TESTING.md).

## Тесты и изоляция от боевой базы

Тесты **никогда** не трогают рабочие `data/anpr.sqlite3`, `data/anpr_state.json` и `data/subscribers.json` —
и не могут повлиять на работающий сервис, камеру и Telegram.

Всё это обеспечивает **безопасный тестовый режим** (`app/core/safe_mode.py`). Он включается
по умолчанию при любом тестовом прогоне — `pytest` и `python -m unittest discover` — и
подключается **до** импорта модулей приложения (`tests/__init__.py` и корневой `conftest.py`),
поэтому пути считаются по изоляции, а не по боевым адресам.

Что делает режим:

| Что | Как |
|---|---|
| рабочие данные | `.env`, база, JSON-состояние, фотографии, подписчики, PID-файл и журналы уводятся во временный каталог |
| секреты | токен Telegram, пароль камеры, чаты обнуляются; читается пустая копия `.env` |
| конфигурация | направление, полосы и часовой пояс заданы явно — результат теста не зависит от вашего `.env` |
| запуск процессов | запрещён (`subprocess.Popen`), в том числе запуск ANPR и `taskkill` |
| сеть | запрещены HTTP-запросы к рабочему сервису, к камере, к Telegram и любому внешнему адресу; RTSP-подключения — тоже |
| управление | запуск и остановка сервиса, подписка на камере — отказ с понятным сообщением |
| фоновые потоки | запоминаются и дожидаются завершения до снятия подмен; если поток не завершился — подмены остаются |

Защита многослойная: даже если прикладной код забудет проверить режим, сетевой уровень
не даст уйти запросу наружу. Явно включить режим можно переменной окружения `ANPR_SAFE_MODE=1`,
выключить — `ANPR_SAFE_MODE=0` (осознанное решение человека, не поведение по умолчанию).

Проверить руками, что прогон безопасен:

```bash
python -c "import os,hashlib;print(hashlib.sha256(open('data/anpr.sqlite3','rb').read()).hexdigest())"
python -m unittest discover -v
python -c "import os,hashlib;print(hashlib.sha256(open('data/anpr.sqlite3','rb').read()).hexdigest())"
```

Хеши (и время изменения файлов) должны совпасть. Заготовка для новых тестов —
`tests.anpr_testenv.IsolatedTestCase`: он подставляет временную базу, временное состояние и
пустой токен Telegram, а заодно проверяет, что предыдущий тест не оставил в модуле подмен.
Доказательства изоляции — в `tests/test_safe_mode.py`.

Локальный запрет коммита при падении тестов — хук `.githooks/pre-commit`. Он смотрит на файлы
в индексе и запускает тесты затронутой области (`scripts/test_select.py`): для правки только
документации — проверку ссылок и smoke-тест, для кода — точечные тесты; полный набор гоняют CI
и проверка перед релизом. Включается один раз:

```bash
git config core.hooksPath .githooks
```

Полную проверку перед релизом (то, что делает CI) можно прогнать одной командой —
`scripts\local_ci.bat`. Он проверяет зависимости, документацию, сверку JSON ↔ SQLite,
все тесты и приёмочный чек-лист без локального сервиса; при первом падении
останавливается и показывает шаг. Полезно, когда GitHub Actions недоступен.

## Если что-то не работает

Посмотрите пояснение в окне. Проверьте питание камеры, сеть и интернет.
Затем нажмите «Перезапустить». Подробности доступны в `data/logs/service.stderr.log`.
Не запускайте отдельно anpr_telegram.py или другие копии Uvicorn одновременно.

## Для обслуживания

Сервис использует только локальный адрес 127.0.0.1:18749, один процесс Uvicorn.
Порт 8000 больше не используется. Если порт занят другой программой, запуск отменяется.
Проверка состояния: http://127.0.0.1:18749/health.
Проверки без камеры: python -m unittest tests.test_stream_latency tests.test_setup_anpr.

Пошаговые регламенты — в [docs/MAINTENANCE.md](docs/MAINTENANCE.md):

- обновление прошивки камеры (что сохранить до, что проверить после, откат);
- замена камеры или перенос на другой адрес/канал;
- ротация фотографий в `data/photos/` (срок хранения 30 дней, ручной и автоматический вариант);
- резервное копирование `.env`, `data/anpr.sqlite3`, `data/anpr_state.json` и журналов;
- порядок обновления зависимостей без «поехавшей» сборки.

### Перенос проекта и откат

Проект переносится целиком: скопировали папку на другой диск — и всё. Пути
считаются от корня проекта, в `.env` они относительные, а пути к фотографиям
в базе — относительные (`ГГГГ-ММ-ДД/файл.jpg`).

Перенос рабочих данных в `data/` (выполнен один раз, с резервной копией):

```bash
python scripts/migrate_data.py --check      # что переносится — без изменений
python scripts/migrate_data.py --migrate    # перенос с проверками
```

Скрипт проверяет, что сервис остановлен, сливает WAL, сверяет целостность
базы и счётчики, копирует файлы, переписывает пути к фотографиям в относительные,
обновляет `.env`, проверяет результат и только потом удаляет оригиналы.
Резервная копия остаётся в `backup/migration-<метка>/`.

Откат — одной командой:

```bash
python scripts/migrate_data.py --rollback backup/migration-20261119_131723
```

Откат возвращает файлы на прежние места, восстанавливает прежние значения
путей в `.env`, удаляет копии из `data/` и проверяет целостность базы.

## Защита от повторов

Первое фото отправляется сразу. Повторы того же номера, полосы и направления объединяются, пока между распознаваниями нет паузы 15 секунд. Интервал задаётся DEDUP_WINDOW_SECONDS в .env. Два настоящих проезда с меньшим интервалом могут объединиться: это правило по времени, а не доказанное отслеживание автомобиля. Повторная передача идентичного JPEG блокируется по SHA-256 в пределах последних 5000 сохранённых ключей, включая перезапуск.

## Два фото в Telegram

Событие отправляется альбомом: основное фото и вырезка номера из того же события. У этой Dahua два JPEG находятся в одном блоке; программа извлекает их по SceneImage и Object.Image. Если вырезки нет, используются координаты номера. При отсутствии подходящих изображений или координат отправляется доступное фото, без выдуманной вырезки.

В заголовке уведомления используется значок шлагбаума `🚧`, а название камеры берётся из `CAMERA_NAME`.

## Добор проездов из архива камеры

После обрыва камеры пропущенное добирается из её собственного архива
(`recordFinder.cgi`, таблица `TrafficSnapEventInfo`).

- **Когда.** Сразу при старте сервиса и далее раз в `BACKFILL_INTERVAL` (60 с).
  Одновременно работает только один сеанс добора; плановый добор и ручной
  `POST /backfill-now` не мешают друг другу — ручной ждёт конца текущего.
- **Что попадает в базу.** Каждая запись архива — одна строка в `events` с флагом
  `backfill = 1`: время, номер, полоса, направление, цвет, тип, номер записи
  архива (`rec_no`). По ключу строки проезд из архива и тот же проезд из live
  — **одна и та же строка**, дублей не возникает.
- **Первый запуск.** Берётся только окно `BACKFILL_LOOKBACK_MINUTES` (180 мин)
  назад; дальше — строго новые записи (`last_rec_no`). Максимальный охват —
  `BACKFILL_MAX_MINUTES` (1440 мин).
- **Время камеры.** Поле `Time` в архиве — настенное время камеры
  (`BACKFILL_TIMESTAMP_MODE=local`), а не UTC. От этого зависят метки в базе.
- **Формат сообщения.** Один текстовый список на всех получателей
  (`kind=backfill` в очереди): время, номер, цвет, тип, направление.
  Если сообщение не доставилось — оно лежит в очереди и уйдёт позже.
- **Фотографии.** **Сама камера снимки из архива не отдаёт**: на этой модели
  `loadfile.cgi?action=downPicByTime` отвечает `501 Not Implemented`. Поэтому
  фотографией архивного проезда может быть только снимок, уже сохранённый
  сервисом. Настройка `BACKFILL_SEND_PHOTOS=true` включает отправку таких
  снимков альбомом вместе со списком (в строке проезда появляется значок 📷);
  при `false` (по умолчанию) добор всегда текстовый.

### Где лежат фотографии

| Что | Где | Настройка |
|---|---|---|
| Снимки проездов | `IMAGE_DIR/ГГГГ-ММ-ДД/*.jpg` (по умолчанию `data/photos`) | `IMAGE_DIR` — можно абсолютный путь |
| Путь к снимку | таблица `passage_photo_paths` в базе (относительный путь) | — |
| Сколько живут каталоги | `IMAGE_RETENTION_DAYS` (30 дней) | удаляет поток обслуживания: на старте и раз в `MAINTENANCE_INTERVAL` (1 ч) |
| Запись снимков | включается `SAVE_PHOTOS` (по умолчанию `true`) | при `false` в мониторинге остаются только фото последних проездов из памяти (не больше 30) |
| Служебные снимки | `data/photos/diagnostic/` | в репозиторий не попадают, в ротацию не входят |

## Направление движения

В «Настройках» выберите «Оба направления», «Только въезд» или «Только выезд», сохраните и нажмите «Перезапустить». Фильтр действует на новые события и добор архива. Неизвестное направление включается только в режиме «Оба направления». Соответствие Obverse/0 въезду и Reverse/1 выезду нужно подтвердить реальным движением для установленной камеры. Старые записи истории сохраняются; отчёт показывает сохранённые проезды, а не заново фильтрует их.

## Если Telegram временно недоступен

Событие и его текст сохраняются в SQLite-очереди (`outbox`). В очередь попадает не только
текст проезда: туда же уходят архивный список из backfill (`kind=backfill`) и дневной отчёт
(`kind=report`). Фотографии в очередь не попадают — очередь хранит только текст.

Очередь развозит отдельный поток с интервалом `OUTBOX_FLUSH_INTERVAL` секунд (по умолчанию 15),
поэтому доставка не зависит от живой камеры: камера может быть недоступна часами, а накопленное
уйдёт сразу после восстановления связи с Telegram. Тот же проход делает цикл камеры — под
замком, поэтому одно и то же сообщение не уходит дважды.

Доставка идёт по чатам, и успех считается по каждому чату отдельно. Если конкретному чату не
удалось отправить фото или альбом, этот чат получает текст проезда в очереди — отдельной записью
с его `chat_id` — и докачивает его позже, когда Telegram доступен. Длинное сообщение уходит
частями по 4000 символов; в очередь кладётся только недоставленный хвост, поэтому уже
доставленное не дублируется.

Неудачные попытки повторяются с экспоненциальной паузой (колонка `next_attempt_at` в базе:
30, 60, 120 … секунд, потолок — `OUTBOX_RETRY_MAX_SECONDS`). Когда число попыток превысило
`OUTBOX_MAX_ATTEMPTS`, запись переходит в статус `dead`: она остаётся в базе, но больше не
отправляется автоматически. Факт появляется в журнале событий (`GET /events`, тип
`telegram_dead`) и в счётчиках `outbox` на `GET /status`. Очередь живёт в SQLite и переживает
рестарт сервиса.

Снимки проездов при этом пишутся на диск в `IMAGE_DIR` (настройка `SAVE_PHOTOS`, по умолчанию
`true`): архив фото не зависит от Telegram, и мониторинг читает фотографии с диска.
При `SAVE_PHOTOS=false` снимки не сохраняются, и в мониторинге остаются только фото последних
проездов, которые ещё лежат в памяти.

Для тестирования в помещении включены ручные снимки из интерфейса камеры (`INCLUDE_MANUAL_SNAPSHOTS=true`). Они считаются тестовыми проездами и могут попасть в отчёт. Для рабочего режима эту настройку можно выключить.

## Эксплуатационная устойчивость

Фоновые потоки сервиса — по одному на задачу, переподключение камеры их не дублирует:

| Поток | Что делает | Как часто |
|---|---|---|
| камера | живая подписка snapManager | постоянно, с переподключением |
| backfill | добор архива камеры | сразу при старте и раз в `BACKFILL_INTERVAL` (60 с) |
| outbox | доставка накопленного | раз в `OUTBOX_FLUSH_INTERVAL` (15 с) |
| report | дневной отчёт | проверка времени раз в `REPORT_CHECK_INTERVAL` (60 с) |
| maintenance | ротация фотографий и чекпоинт WAL | `MAINTENANCE_INTERVAL` (1 ч) и `WAL_CHECKPOINT_INTERVAL` (15 мин) |

**Отчёт за день** уходит отдельным потоком, а не «точным совпадением минуты» в цикле камеры.
Как только наступило `REPORT_TIME` (20:00), отчёт уходит в течение минуты и только один раз
за день. Если сервис был выключен в это время, отчёт догоняет: уходит за сегодняшний день,
а если не ушёл и за вчерашний — уходит и за вчерашний. Отметки об отправленных отчётах
хранятся в `data/anpr_state.json` (`reported_days`), поэтому перезапуск дубли не создаёт.

Отчёт приходит **XLSX-файлом** с двумя вкладками: «Итоги» (всего проездов, разных
номеров, средняя скорость) и «Проезды» (время, номер, цвет, тип, скорость, направление,
полоса, источник). К файлу добавляется краткая подпись со сводкой. Генератор
`app/core/report_xlsx.py` не требует новых пакетов. Если Telegram не принял файл,
отчёт уходит текстом через существующую очередь недоставленных сообщений — данные
не теряются. Текстовый вид в консоли и в `--report-now --dry-run` сохраняется.

**Журналы** `data/logs/service.stdout.log` и `data/logs/service.stderr.log` ротируются по размеру: файл
`LOG_MAX_MB` (10 МБ), старые копии — `.1`, `.2`, `.3` (`LOG_BACKUPS`). Плюс `data/logs/service.boot.log` —
вывод процесса до старта журналов (ошибки запуска).

**Фотографии** в `data/photos/ГГГГ-ММ-ДД/` живут `IMAGE_RETENTION_DAYS` дней (30). Старые каталоги
удаляет поток обслуживания (сразу при старте и далее раз в `MAINTENANCE_INTERVAL`).
Папка `data/photos/diagnostic/` — служебная, в репозиторий не попадает.

**База** `data/anpr.sqlite3` работает в режиме WAL. Поток обслуживания периодически делает
`wal_checkpoint(TRUNCATE)`, поэтому файл `data/anpr.sqlite3-wal` не растёт без предела.
Индексы `idx_events_day` и `idx_events_captured_at` ускоряют отчёты и выборки за день.

**Остановка** — мягкая: панель управления вызывает `POST /shutdown` с секретным токеном, сервис
останавливает потоки, пишет `data/anpr_state.json` и закрывает базу. Жёсткое завершение используется
только если сервис не освободил порт за 20 секунд — и только для подтверждённого своего процесса.

**Один экземпляр сервиса.** Сервис держит именованный мютекс Windows (`Local\EvrikaService_*`).
Второй экземпляр на этой машине не запустится: он завершится с сообщением, вместо того чтобы
портить рабочую базу и бороться за порт. Формат PID-файла прежний — одна строка с номером
процесса в `data/runtime/service.pid`.

**Чужой процесс не трогаем.** Совпадение порта само по себе ничего не значит. Перед остановкой
проверяются три вещи: PID из `/health` совпадает с PID из `data/runtime/service.pid`, процесс жив, а его
командная строка указывает на `app.py`. Если это не наш процесс — остановка отменяется с
записью в журнал аудита.

**Журналы управления** — структурированные, в формате JSONL (одна запись на строку):

| Файл | Что в нём |
|---|---|
| `data/logs/service.control.log` | операции управления сервисом: запуск, остановка, перезапуск, запросы остановки, отказы авторизации |
| `data/logs/panel.log` | события панели: запрос подтверждения и ответ пользователя, завершение операции, завершение панели |

Каждая запись: время ISO 8601 с часовым поясом, действие, источник, PID инициатора,
PID целевого процесса, результат (`requested` / `ok` / `error` / `denied`), длительность
и причина ошибки. Секреты в журналы не попадают: поля `token`, `password`, `secret` и подобные
маскируются, из текста ошибок вычищаются токены бота, пароли и учётные данные из адресов.
Журналы ротируются по размеру (5 МБ, 3 копии).

## Приёмка в бой

Перед переходом в боевой режим сервис проходит приёмочный чек-лист: 24 часа
непрерывной работы, сверка JSON/SQLite, имитация обрыва камеры и Telegram,
уход дневного отчёта, работа дашборда и фотоархива, доставка события всем
получателям.

- Полный чек-лист (ручные шаги и ожидаемые результаты): [docs/ACCEPTANCE.md](docs/ACCEPTANCE.md).
- Автоматическая часть: `python scripts/acceptance_check.py` — сверка источников,
  очередь доставки, отчёт, фотоархив, получатели, живой сервис.
  Код 0 — блокирующих замечаний нет.
- Сверка источников отдельно: `python scripts/verify_state.py` (код 1 при расхождениях).

## Состав репозитория

Код приложения лежит в пакете `app/` (ниже — назначение каждого модуля одной
строкой; подробная навигация по функциям, связям и тестам — в
[docs/CODEMAP.md](docs/CODEMAP.md), правила работы ИИ-агентов с проектом — в
[AGENTS.md](AGENTS.md)):

```
app/
├── core/       ядро: anpr_telegram.py (сбор проездов), paths.py (пути),
│               system_events.py (журнал событий), preferences.py (автозапуск
│               Windows и настройки панели), safe_mode.py (безопасный
│               тестовый режим), window_state.py (положение и размер окна)
├── services/   http_api.py (HTTP-сервис), control.py (запуск и остановка),
│               logs.py (журналы с ротацией), audit.py (журналы управления
│               в JSONL), auth.py (токен управления), instance.py (один
│               экземпляр сервиса), process_info.py (проверка процессов),
│               panel_lock.py (один экземпляр панели)
├── storage/    database.py (SQLite), photo_archive.py, passage_photos.py,
│               event_images.py
└── ui/         shell.py (единое окно), header.py (шапка с индикаторами),
                service_panel.py (панель управления), status.py (состояния),
                dashboard.py (мониторинг), settings.py (настройки),
                widgets.py, motion.py, icons.py, theme.py, tklife.py,
                schedule.py (отложенные вызовы Tk)
```

- В корне — совместимые точки входа: `app.py` (HTTP-сервис), `control_panel.py`
  (панель управления — её запускают `run.bat` и автозапуск Windows),
  `setup_anpr.py` (настройки — их запускает `settings.bat`), `anpr_telegram.py`
  (CLI ядра: `--check`, `--report-now`, `--dry-run`, `--parser-test`,
  `--backfill-now`). Это тонкие лаунчеры: они запускают код из `app/` и
  подставляют тот же объект модуля в `sys.modules` — поэтому `import
  anpr_telegram` и подмены вида `patch.object(bot, 'STORE')` работают как
  раньше.
- `scripts/` — служебные сценарии: сверка состояния, приёмка, проверка
  согласованности зависимостей.
- `tests/` — автоматические тесты и изоляция от боевой базы.
- `assets/` — иконки и логотипы, которые использует интерфейс.
- `data/` — каталог изменяемых данных: база, зеркало состояния, подписчики,
  фотографии, PID-файл, токен управления и журналы. Содержимое в Git не
  попадает (в репозитории остаётся только `data/README.md`).
- `backup/` — резервные копии переноса рабочих данных (создаёт
  `scripts/migrate_data.py`; в Git не попадает).
- `filled/` — набор иконок Material Symbols (~1050 файлов). Полный набор в
  репозиторий **не входит**: в `.gitignore` оставлены только те иконки, что
  реально рисуются, и `LICENSE`/`README.md` набора. Остальное берётся из
  исходного набора при необходимости.
- Рабочие данные в репозиторий не попадают: `*.log`, `.env`, содержимое `data/`
  и `backup/` — всё в `.gitignore`.
- Локальные заметки (`PROJECT_CONTEXT.md`, `Dahua-API-Python-Integration.SKILL.md`)
  и макеты (`*.pdf`, `*.html`, `evrika-*.png`) тоже не коммитятся.
