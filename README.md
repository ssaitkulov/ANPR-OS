# Камера и Telegram

## Как пользоваться

Откройте **run.bat**. Откроется окно управления, сбор запустится автоматически.

- **Программа работает** — сборщик запущен.
- **Камера подключена** — соединение с камерой установлено.
- **Telegram ожидает первую отправку** — доставка после запуска ещё не проверена.
- **Последнее уведомление доставлено** — Telegram принял уведомление хотя бы для одного разрешённого чата.
- **Остановить сбор** — прекратить получение событий.
- **Перезапустить** — остановить сбор и запустить заново с сохранёнными настройками.
- **Настройки** — изменить камеру, токен и разрешённые чаты.

Окно можно закрыть: сбор продолжится. После перезагрузки Windows откройте run.bat.
Автоматический запуск при включении компьютера включается переключателем «Запускать с Windows»
в окне «Настройки»: программа регистрирует себя в автозагрузке Windows (HKCU\...\Run).

## Настройки

Адрес камеры, логин, пароль, токен Telegram, ID чата и список разрешённых чатов.
Для личного использования укажите свой ID в обоих полях и напишите боту /start.
В разрешённой группе команды доступны всем участникам группы.
После сохранения нажмите «Перезапустить» в окне управления.
Секреты находятся в локальном .env без шифрования. Не передавайте этот файл другим.

## Telegram

/start — подписаться; /stop — отписаться от подписки; /report — отчёт за сегодня.
Основной чат из настроек получает события независимо от подписки.
Направление движения и часы камеры ещё требуют проверки реальным проездом.

## Где хранятся проезды

**`anpr.sqlite3` — единственный источник истины.** В таблице `events` одна строка = один проезд
(и live-событие, и запись из архива камеры). Ключ строки — `sha256(день|время|номер|полоса|направление)`,
то есть строится из самого проезда, поэтому повторные проезды с одним и тем же `GroupID` прошивки
не теряются. Идентификаторы прошивки хранятся отдельно и в ключ не входят:
`source_key` = `GroupID:IndexInGroup:номер:полоса`, `group_id` = сам `GroupID`,
`rec_no` = номер записи в архиве камеры (у проездов из архива). Схема и старые ключи
пересчитываются при старте — миграция идемпотентная (`storage.py`).
Фотографии лежат файлами в `images/` (в базе — только пути). Запись снимков на диск
включается настройкой `SAVE_PHOTOS` (по умолчанию `true`); выключается только осознанно,
иначе мониторинг не сможет показать фото проезда.

`anpr_state.json` — рабочее зеркало: окно дедупликации, отпечатки снимков, `last_rec_no`,
`last_report_date`. Проезды в нём хранятся последние `STATE_KEEP_DAYS` дней (по умолчанию 30)
и служат страховкой на случай сбоя записи в базу; при старте и раз в минуту записи
синхронизируются в базу.

Отчёт в Telegram, `/status`, `/entries/today` и мониторинг читают один и тот же SQLite.

Сверка двух источников (JSON-зеркало ↔ SQLite) — `python tools/verify_state.py`:
печатает расхождения и возвращает код 1, если они есть.

## Локальные эндпоинты

Сервис слушает только `127.0.0.1:18749` — наружу ничего не отдаётся. Все эндпоинты читают
и пишут ту же базу `anpr.sqlite3`, что и мониторинг.

| Метод и путь | Что делает | Пример |
|---|---|---|
| `GET /health` | Состояние процесса, камеры и Telegram, время запуска | `curl http://127.0.0.1:18749/health` |
| `GET /status` | Сводка за сегодня: число въездов, уникальные номера, статистика, аптайм | `curl http://127.0.0.1:18749/status` |
| `GET /entries/today` | Список проездов за сегодня (время, номер, полоса, направление) | `curl http://127.0.0.1:18749/entries/today` |
| `GET /passages` | Последние проезды из базы (для ленты мониторинга) | `curl http://127.0.0.1:18749/passages` |
| `GET /passages/{id}/photo` | Фотография проезда по его id (JPEG); 404, если файла уже нет | `curl -o p.jpg http://127.0.0.1:18749/passages/12/photo` |
| `GET /events` | Журнал операционных событий (`?after=id` — только новые) | `curl "http://127.0.0.1:18749/events?after=0"` |
| `POST /report-now` | Отправить отчёт за сегодня в Telegram сейчас | `curl -X POST http://127.0.0.1:18749/report-now` |
| `POST /backfill-now` | Запустить добор архива камеры сейчас | `curl -X POST http://127.0.0.1:18749/backfill-now` |
| `POST /shutdown` | Мягко остановить сервис (потоки, состояние, база) | `curl -X POST http://127.0.0.1:18749/shutdown` |

`/report-now` и `/backfill-now` возвращают сразу и выполняют работу в фоне:
отчёт приходит в Telegram, список архивных проездов — тем же списком, что и при плановом доборе.
`/shutdown` останавливает сервис штатно: фоновые потоки дорабатывают операцию, состояние
пишется в `anpr_state.json`, база закрывается, процесс завершается сам.

## Зависимости и версии

Проверенная среда: Python 3.14.7 (Windows 11 x64).

- `requirements.txt` — прямые зависимости с верхними границами (`requests>=2.32,<3` и т.д.).
  Границы обязательны: без них новая версия пакета может сломать проверенную сборку.
- `requirements-lock.txt` — точные версии проверенного окружения (вместе с транзитивными).
  Установка: `python -m pip install -r requirements-lock.txt`.
- `pyproject.toml` — метаданные проекта, `requires-python = ">=3.11,<3.15"` и тот же набор зависимостей.
- `run.bat` доустанавливает `requirements.txt` сам, если чего-то не хватает.

Для тестов: `python -m unittest discover -v` (полный набор) или `python -m pytest -q`
(тот же набор другим раннером); быстрая проверка без камеры —
`python -m unittest test_stream_latency test_setup_anpr`. CI (.github/workflows/ci.yml) гоняет
`python -m unittest discover -v` на Windows для Python 3.11, 3.12, 3.13 и 3.14, проверяет
`pip check` и то, что тесты не создали `anpr.sqlite3` / `anpr_state.json` в рабочей папке.

## Тесты и изоляция от боевой базы

Тесты **никогда** не трогают рабочие `anpr.sqlite3`, `anpr_state.json` и `subscribers.json`.
Изоляция живёт в модуле `anpr_testenv.py`: он перенаправляет пути базы, состояния, фотографий
и подписчиков во временный каталог и обнуляет токен Telegram. Каждый тестовый файл импортирует
`anpr_testenv` **первым** — до `import anpr_telegram` (иначе модуль возьмёт боевые пути при импорте).

Проверить руками, что прогон безопасен:

```bash
python -c "import os,hashlib;print(hashlib.sha256(open('anpr.sqlite3','rb').read()).hexdigest())"
python -m unittest discover -v
python -c "import os,hashlib;print(hashlib.sha256(open('anpr.sqlite3','rb').read()).hexdigest())"
```

Хеши (и время изменения файлов) должны совпасть. Заготовка для новых тестов —
`anpr_testenv.IsolatedTestCase`: он подставляет временную базу, временное состояние и
пустой токен Telegram, а заодно проверяет, что предыдущий тест не оставил в модуле подмен.

Локальный запрет коммита при падении тестов — хук `.githooks/pre-commit`. Включается один раз:

```bash
git config core.hooksPath .githooks
```

## Если что-то не работает

Посмотрите пояснение в окне. Проверьте питание камеры, сеть и интернет.
Затем нажмите «Перезапустить». Подробности доступны в service.stderr.log.
Не запускайте отдельно anpr_telegram.py или другие копии Uvicorn одновременно.

## Для обслуживания

Сервис использует только локальный адрес 127.0.0.1:18749, один процесс Uvicorn.
Порт 8000 больше не используется. Если порт занят другой программой, запуск отменяется.
Проверка состояния: http://127.0.0.1:18749/health.
Проверки без камеры: python -m unittest test_stream_latency test_setup_anpr.

Пошаговые регламенты — в [docs/MAINTENANCE.md](docs/MAINTENANCE.md):

- обновление прошивки камеры (что сохранить до, что проверить после, откат);
- замена камеры или перенос на другой адрес/канал;
- ротация фотографий в `images/` (срок хранения 30 дней, ручной и автоматический вариант);
- резервное копирование `.env`, `anpr.sqlite3`, `anpr_state.json` и журналов;
- порядок обновления зависимостей без «поехавшей» сборки.

## Защита от повторов

Первое фото отправляется сразу. Повторы того же номера, полосы и направления объединяются, пока между распознаваниями нет паузы 15 секунд. Интервал задаётся DEDUP_WINDOW_SECONDS в .env. Два настоящих проезда с меньшим интервалом могут объединиться: это правило по времени, а не доказанное отслеживание автомобиля. Повторная передача идентичного JPEG блокируется по SHA-256 в пределах последних 5000 сохранённых ключей, включая перезапуск.

## Два фото в Telegram

Событие отправляется альбомом: основное фото и вырезка номера из того же события. У этой Dahua два JPEG находятся в одном блоке; программа извлекает их по SceneImage и Object.Image. Если вырезки нет, используются координаты номера. При отсутствии подходящих изображений или координат отправляется доступное фото, без выдуманной вырезки.

В заголовке уведомления используется значок шлагбаума `🚧`, а название камеры берётся из `CAMERA_NAME`.

## Направление движения

В «Настройках» выберите «Оба направления», «Только въезд» или «Только выезд», сохраните и нажмите «Перезапустить». Фильтр действует на новые события и добор архива. Неизвестное направление включается только в режиме «Оба направления». Соответствие Obverse/0 въезду и Reverse/1 выезду нужно подтвердить реальным движением для установленной камеры. Старые записи истории сохраняются; отчёт показывает сохранённые проезды, а не заново фильтрует их.

## Если Telegram временно недоступен

Событие и его текст сохраняются в SQLite-очереди (`outbox`). В очередь попадает не только
текст проезда: туда же уходят архивный список из backfill (`kind=backfill`) и дневной отчёт
(`kind=report`). Фотографии в очередь не попадают — очередь хранит только текст.

Очередь развозит отдельный поток с интервалом `OUTBOX_FLUSH_INTERVAL` секунд (по умолчанию 15),
поэтому доставка не зависит от живой камеры: камера может быть недоступна часами, а накопленное
уйдёт сразу после восстановления связи с Telegram. Тот же проход делает цикл камеры — под
замком, поэтому одно и то же сообщение не уходит дважды.

Доставка идёт по чатам, и успех считается по каждому чату отдельно. Если конкретному чату не
удалось отправить фото или альбом, этот чат получает текст проезда в очереди — отдельной записью
с его `chat_id` — и докачивает его позже, когда Telegram доступен. Длинное сообщение уходит
частями по 4000 символов; в очередь кладётся только недоставленный хвост, поэтому уже
доставленное не дублируется.

Неудачные попытки повторяются с экспоненциальной паузой (колонка `next_attempt_at` в базе:
30, 60, 120 … секунд, потолок — `OUTBOX_RETRY_MAX_SECONDS`). Когда число попыток превысило
`OUTBOX_MAX_ATTEMPTS`, запись переходит в статус `dead`: она остаётся в базе, но больше не
отправляется автоматически. Факт появляется в журнале событий (`GET /events`, тип
`telegram_dead`) и в счётчиках `outbox` на `GET /status`. Очередь живёт в SQLite и переживает
рестарт сервиса.

Снимки проездов при этом пишутся на диск в `IMAGE_DIR` (настройка `SAVE_PHOTOS`, по умолчанию
`true`): архив фото не зависит от Telegram, и мониторинг читает фотографии с диска.
При `SAVE_PHOTOS=false` снимки не сохраняются, и в мониторинге остаются только фото последних
проездов, которые ещё лежат в памяти.

Для тестирования в помещении включены ручные снимки из интерфейса камеры (`INCLUDE_MANUAL_SNAPSHOTS=true`). Они считаются тестовыми проездами и могут попасть в отчёт. Для рабочего режима эту настройку можно выключить.

## Эксплуатационная устойчивость

Фоновые потоки сервиса — по одному на задачу, переподключение камеры их не дублирует:

| Поток | Что делает | Как часто |
|---|---|---|
| камера | живая подписка snapManager | постоянно, с переподключением |
| backfill | добор архива камеры | сразу при старте и раз в `BACKFILL_INTERVAL` (60 с) |
| outbox | доставка накопленного | раз в `OUTBOX_FLUSH_INTERVAL` (15 с) |
| report | дневной отчёт | проверка времени раз в `REPORT_CHECK_INTERVAL` (60 с) |
| maintenance | ротация фотографий и чекпоинт WAL | `MAINTENANCE_INTERVAL` (1 ч) и `WAL_CHECKPOINT_INTERVAL` (15 мин) |

**Отчёт за день** уходит отдельным потоком, а не «точным совпадением минуты» в цикле камеры.
Как только наступило `REPORT_TIME` (20:00), отчёт уходит в течение минуты и только один раз
за день. Если сервис был выключен в это время, отчёт догоняет: уходит за сегодняшний день,
а если не ушёл и за вчерашний — уходит и за вчерашний. Отметки об отправленных отчётах
хранятся в `anpr_state.json` (`reported_days`), поэтому перезапуск дубли не создаёт.

**Журналы** `service.stdout.log` и `service.stderr.log` ротируются по размеру: файл
`LOG_MAX_MB` (10 МБ), старые копии — `.1`, `.2`, `.3` (`LOG_BACKUPS`). Плюс `service.boot.log` —
вывод процесса до старта журналов (ошибки запуска).

**Фотографии** в `images/ГГГГ-ММ-ДД/` живут `IMAGE_RETENTION_DAYS` дней (30). Старые каталоги
удаляет поток обслуживания (сразу при старте и далее раз в `MAINTENANCE_INTERVAL`).
Папка `images/diagnostic/` — служебная, в репозиторий не попадает.

**База** `anpr.sqlite3` работает в режиме WAL. Поток обслуживания периодически делает
`wal_checkpoint(TRUNCATE)`, поэтому файл `anpr.sqlite3-wal` не растёт без предела.
Индексы `idx_events_day` и `idx_events_captured_at` ускоряют отчёты и выборки за день.

**Остановка** — мягкая: панель управления вызывает `POST /shutdown`, сервис останавливает
потоки, пишет `anpr_state.json` и закрывает базу. Жёсткое завершение используется только
если сервис не освободил порт за 20 секунд.
