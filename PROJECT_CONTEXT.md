## 1. Что делает система
Dahua ANPR-камера → Python-скрипт (`anpr_telegram.py`) → Telegram-бот (ник и id — в `.env`).

- Каждый въезд (`TrafficJunction`) → **альбом из 2 снимков** (сцена + вырезка) + текст: 🚗 ВЪЕЗД · номер / 🕐 время / 🎯 Уверенность / 🚙 скорость / 🎨 цвет·тип.
- В **20:00** — итог дня всем подписчикам (въездды, уникальные номера, средняя скорость, список).
- После обрыва — **backfill**: добор из архива камеры одним текстовым списком.
- Подписчики: `/start` — подписка, `/stop` — отписка, `/report` — отчёт дня. Рассылка — всем подписчикам + `TELEGRAM_CHAT_ID`.

## 4. Логика сбора (`app/core/anpr_telegram.py`, ~2100 строк)
- **Дедуп live:** по `GroupID:IndexInGroup:PlateNumber`; fallback — номер+полоса+минута. **Дедуп backfill:** по `RecNo` (`last_rec_no` в state) + сверка с live (±120 с, тот же номер).
- **Фильтры:** `DIRECTION=Approach` (Приближается/Въезд; поля: `Direction, TrafficCar.Direction, DrivingDirection` и др. — **реальное имя поля не подтверждено**, нужна raw-проездка); `ALLOWED_LANES` пусто = все. Отброшенные события теперь логгируются: `[filter] ...`.
- **Направление архива:** `JunctionDirection 0 = Въезд, 1 = Выезд` — **предположение** (0 преобладает). Требует подтверждения реальным выездом.
- **Confidence:** в live-тексте ожидаем `TrafficCar.Confidence`, но у камеры этого поля пока не видно — в подписи показывает `—`. Нужна raw-проездка (`DEBUG_RAW=true`) для подтверждения.
- **Backfill:** фон-поток при (ре)старте (live не ждёт) и раз в 60 с; одновременно работает только один сеанс добора. Первый запуск — только за `BACKFILL_LOOKBACK_MINUTES=180`, далее строго новые `RecNo`. Одним списком, без фото. Записи архива **пишутся в SQLite** (флаг `backfill=1`, ключ `backfill:rec:<RecNo>`); если тот же проезд затем приходит live — обновляется та же строка, а не заводится дубль.
- **Рассылки:** `telegram_send`/`telegram_send_photo`/`telegram_send_media_group` — итерация по получателям (`TELEGRAM_CHAT_ID` + подписчики). `poll_telegram_updates` — long-poll `getUpdates`.
- **Состояние:** `data/anpr_state.json` (дни, `seen`, `last_event_time`, `last_rec_no`, `last_report_date`).
- **Ключ события (Этап 0, 18.11):** `events.event_key` = `sha256(day|iso|plate|lane|direction)` — контентный, `GroupID` прошивки в ключ не входит (он переиспользуется). Идентификаторы прошивки в отдельных колонках: `source_key` (`GroupID:IndexInGroup:номер:полоса`), `group_id`, `rec_no` (номер записи архива). Горячая идемпотентная миграция — в `app/storage/database.py` (`Store.__init__`).
- **Сверка источников:** `python scripts/verify_state.py` — JSON-зеркало ↔ SQLite, код 1 при расхождении.

## 7. Этап 2 — эксплуатационная устойчивость (18.11)

- **Потоки сервиса** — по одному на задачу, `start_worker()` не даёт создать второй: камера, backfill, outbox, report, maintenance. Переподключение камеры потоки не плодит.
- **Backfill:** сеть (`recordFinder`) идёт **без** общего замка состояния — камера не ждёт скачивание архива; запись найденного под `STATE_LOCK`. Один сеанс — `_backfill_lock` (`run_backfill(wait_seconds=...)` ждёт освобождения для ручного `/backfill-now`).
- **Отчёт 20:00** — отдельный поток `report_worker`, проверка раз в `REPORT_CHECK_INTERVAL` (60 с), а не «точное совпадение минуты» в цикле камеры. Окно `REPORT_WINDOW_MINUTES` (240 мин) после `REPORT_TIME`; **catch-up**: если за вчера отчёт не ушёл (сервис был выключен) — уходит за вчера. Отметки — `reported_days` в `data/anpr_state.json`.
- **Журналы:** `app/services/logs.py` — писатель на файл на базе `RotatingFileHandler` (`LOG_MAX_MB`=10, `LOG_BACKUPS`=3 → `.1`, `.2`, `.3`). `sys.stdout/sys.stderr` сервиса заменены на эти файлы; журнал uvicorn идёт туда же (`BridgeHandler`, access-строки отключены). Вывод до старта журналов — `data/logs/service.boot.log`.
- **Фотографии:** `cleanup_old_photos()` удаляет каталоги старше `IMAGE_RETENTION_DAYS` (30) — на старте и раз в `MAINTENANCE_INTERVAL`; `images/diagnostic` в `.gitignore`.
- **База:** индексы `idx_events_day`, `idx_events_captured_at` (старые `events_day_idx`/`events_capture_idx` удалены), периодический `wal_checkpoint(TRUNCATE)` (`WAL_CHECKPOINT_INTERVAL`=900 с).
- **Остановка мягкая:** `POST /shutdown` → uvicorn завершается штатно → `request_stop()` → потоки → `save_state` → `STORE.close()`. `service_control.stop()` шлёт `/shutdown` и ждёт порт 20 с; `taskkill /F` — только последний резерв. Сервис запускается как `python app.py` (нужен объект `uvicorn.Server`).

### Новая структура

Состав модулей на момент этапа; сегодня их больше — актуальная карта в
[docs/CODEMAP.md](docs/CODEMAP.md).

```
app/core/       anpr_telegram.py (ядро), paths.py (пути), system_events.py, preferences.py
app/services/   http_api.py, control.py, logs.py, panel_lock.py
app/storage/    database.py, photo_archive.py, passage_photos.py, event_images.py
app/ui/         panel.py, dashboard.py, settings.py
scripts/        verify_state.py, acceptance_check.py, check_lock.py   (было tools/)
tests/          test_*.py, anpr_testenv.py, conftest.py
data/           каталог изменяемых данных (пока пуст, миграция не согласована)
```
Корень — совместимые точки входа: `app.py`, `control_panel.py`, `setup_anpr.py`,
`anpr_telegram.py`, `service_control.py`. Это тонкие лаунчеры.

### Ключевое решение: алиас в sys.modules
Лаунчеры не просто импортируют функции, а подставляют **тот же объект
модуля**: `sys.modules['anpr_telegram'] = app.core.anpr_telegram` и т.д.
Это обязательно: тесты подменяют атрибуты модуля
(`patch.object(bot, 'STORE')`, `patch('control_panel.service.stop')`) — при
простом `from … import *` подменился бы один модуль, а работал бы другой,
и часть тестов проходила бы «вхолостую», а изоляция — перестала бы
изолировать (реальная БД попадала бы под тесты).

### Пути
`app/core/paths.py` — единственный источник путей: `PROJECT_ROOT`, `DATA_DIR`,
`PHOTO_DIR`, `RUNTIME_DIR`, `LOG_DIR`, `ASSETS_DIR`, `resolve_path()`,
`resolve_photo_path()`, `relative_photo_path()`. Все пути считаются от корня
проекта, а не от текущей директории: относительный
`SUBSCRIBERS_FILE=data/subscribers.json` в `.env` разрешается от корня
(раньше — от CWD, т.е. зависел от места запуска). Ни один модуль не вычисляет
корень проекта самостоятельно (проверяется тестом `tests/test_paths.py`).

### Что НЕ менялось
- Точки входа: `run.bat`, `settings.bat`, `start_service.ps1`, `python app.py`,
  `python anpr_telegram.py --check`, команда `anpr-service`, автозапуск Windows
  (путь к `control_panel.py` в реестре прежний).
- Имя мютекса панели (`sha256` от корня проекта) прежнее — ранее запущенная
  панель узнаётся новой.
- Обработчик журналов: строка класса в конфигурации uvicorn теперь
  `app.services.logs.BridgeHandler`.

## 15. Этап 2.5 — диагностика Telegram: «Соединение» и «Последняя доставка» (19.11)

Запрос: у успешной отправки нет гарантии, что Telegram доступен дальше.
До правки индикатор Telegram в шапке зеленел по факту последней доставки:
после одной удачной отправки он мог показывать «Работает» сутками, хотя сеть
легла. Обратная сторона: до первой отправки панель писала «Нет соединения»
при вполне рабочем Telegram.

### Что сделано

**Разделены два диагноза.**
- `Соединение` — доступен ли API сейчас. Отдельное состояние в
  `RUNTIME['telegram_connection']`: `ok`, `at` (последний успешный контакт),
  `failed_at`, `error`.
- `Последняя доставка` — ушло ли сообщение. Прежний
  `RUNTIME['telegram_delivery']` без изменений.

**Сервис следит за связью.** `app/core/anpr_telegram.py`: все обращения к
Telegram API идут через `_telegram_call()` — он запоминает результат в
`telegram_connection`. Ответ сервера — связь есть; сетевая ошибка — связи нет.
Долгий опрос обновлений (`getUpdates`) отвечает раз в ~30 с, поэтому его
таймаут — это «не дождались ответа», а не обрыв: он не роняет индикатор, но
записывается в `error`. Обрывом считается молчание дольше
`CONNECTION_STALE_SEC` (90 с = три пропуска опроса подряд) — иначе при
отсутствии проездов обрыв связи был бы не виден вовсе.

**Интерфейс.** `app/ui/status.py` — `telegram_connection_view()` и
`telegram_delivery_view()` дают два независимых статуса с собственными
цветами; `telegram_view()` (индикатор в шапке) отвечает на вопрос «доступен ли
Telegram сейчас» и показывает красным обрыв связи, а ошибку доставки — тоже
красным, но отдельной строкой в подробностях. Без контакта с Telegram
индикатор пишет «Проверяем…», а не «Нет соединения» (нет данных ≠ нет связи).
`app/ui/shell.py` — в панели подробностей Telegram появились строки
«Соединение», «Последняя связь», «Последняя доставка», «Ошибка связи».

**Побочное исправление: токен бота больше не попадает в тексты ошибок.**
urllib3 пишет в исключении полный адрес запроса, а в нём — токен бота.
`_short_error()` оставляет суть ошибки (120 символов) и заменяет токен на
`***`; тем же текстом пишутся строки `[telegram] …` в журнале.

### Проверено вживую

- Обрыв Telegram сымитирован через `HTTPS_PROXY` на закрытый порт (камера по
  HTTP не затронута): `/health` отдал `ok: false` с текстом ошибки, панель
  показала «Соединение: Нет», «Ошибка связи: ProxyError(…)» — при живом
  состоянии «Доставлено» в соседней строке.
- После восстановления связи индикатор снова «Работает», «Соединение: Есть».
- Реальная рассылка (`/report-now`) обновила только доставку:
  «Последняя доставка: Доставлено (1 / 0)», связь осталась «Есть».
- В `/health` и в новых строках журнала токена бота нет.
- Тесты: 305 (было 297) — `TelegramConnectionTests` (7) в
  `tests/test_stage3_quality.py`, `test_telegram_connection_and_delivery_are_separate_diagnostics`
  в `tests/test_stage2_ui.py`, правки `tests/test_panel_status.py`.

каждый компонент показывает только своё состояние.

**Управление — в раскрывающейся панели.** `app/ui/service_panel.py`:
панель внутри окна (`CTkFrame`, без нового `CTkToplevel`), шириной 440 px,
выравнена по правому краю шапки, не сдвигает Dashboard и не перекрывает
кнопки окна. Открывается кнопкой «Управление» и нажатием на любой
индикатор, закрывается повторным нажатием, Escape, кликом вне панели и
сменой раздела. Три секции: ANPR-сервис (PID, время работы, порт, время
последней успешной проверки), камера (имя, IP, приём ANPR-событий, время
последнего события) и Telegram (соединение, время последней связи, время
последней доставки, доставлено/ошибок). Показателей, которых нет в данных,
панель не показывает.

**Состояния — по ТЗ, а не по прежним словам.**
- Сервис: «Работает», «Остановлен», «Запускается», «Останавливается»,
  «Перезапускается», «Ошибка».
- Камера: «Подключена», «Нет связи», «Подключение», «Неизвестно».
- Telegram: «Работает», «Недоступен», «Проверка», «Неизвестно»
  (плюс «Не настроен», если не задан токен — состояние известно точно).
- Сервис остановлен — состояния камеры и Telegram «Неизвестно»: подтверждённого
  обрыва связи у нас нет, а устаревшие данные показывать нельзя.
- Ошибка доставки Telegram больше не красит индикатор в шапке: доступность
  канала и успешность последней отправки — разные диагнозы (доставка видна
  в панели отдельными строками).

**Кнопки по состоянию.** Работает — «Перезапустить», «Остановить» (красная
семантика), «Журнал»; остановлен — «Запустить» (жёлтый CTA), «Журнал»; во
время операции — текущая операция, заблокированные кнопки и ненавязчивая
полоска выполнения; в ошибке — причина и действие восстановления, выбранное
по фактическому состоянию процесса (`process_info.pid_alive` +
`looks_like_service`), а не вслепую.

**Сообщение о результате операции.** В панели под кнопками появляется
строка результата: при ошибке — красный текст со знаком `alert-triangle` и
конкретной причиной, при успехе — `circle-check` и текст («ANPR-сервис
остановлен.»). Панель открывается сама только при ошибке. Автоматический
запуск сервиса при старте приложения результата не показывает: сообщение
пользователю ничего не даёт.

**Подтверждения.** Остановка — «Остановить ANPR-сервис?» / «Распознавание
номеров и обработка новых событий будут приостановлены до повторного
запуска.»; перезапуск — «Перезапустить ANPR-сервис?» / «Во время перезапуска
обработка событий может быть временно недоступна.» Механизм остался
системным (`messagebox.askyesno`), поэтому подписи кнопок задаёт Windows
(«Да»/«Нет»); управляющий запрос `/shutdown` уходит только после ответа
пользователя, авторизация токеном не менялась.

**Оформление.** `app/ui/theme.py` — единые токены: фон `#101827`, карточка
`#1B293D`, вложенные элементы `#26364C`, текст `#F2F9FF`, вторичный текст
`#A9BEDB`, акцент `#0089FF`, CTA `#FEE46F`; состояния — `#06C35D` / `#FFBA02` /
`#F23F3A` / `#0089FF` / `#A9BEDB`. Обводок нет (`border_width=0`), разделений
нет — только фон, отступы и типографика. Видимый фокус с клавиатуры сохранён
(`app/ui/widgets.py`).

**Иконки.** `app/ui/icons.py` — централизованный кэш: PNG-силуэты из
`assets/icons/` (Tabler Filled, растеризованы скриптом
`scripts/rasterize_icons.py`), перекрашиваются в цвет состояния и кэшируются
по паре «иконка + цвет + размер». Кэш привязан к интерпретатору Tk: в процессе
может быть несколько окон (тесты), и снимок Tk живёт в одном интерпретаторе.

**Никаких «invalid command name».** Проверено отдельно: заголовок
интерфейса и панель перестают реагировать на события до отмены отложенных
вызовов (`SystemHeader.closed`), при закрытии окна отложенные вызовы
отменяются ещё раз — уже после уничтожения виджетов (уничтожение шлёт
Configure-события, на них интерфейс мог бы запланировать новые вызовы).
Дополнительно `app/ui/schedule.py` делает имена команд обратных вызовов
Tkinter уникальными: имя строится из идентификатора одноразового объекта,
а идентификаторы переиспользуются — из-за этого таймер мог вызвать уже
удалённую команду (чужой обработчик и ошибка в stderr).

**Анимации.** `app/ui/motion.py` — только `after()`, без потоков: появление
панели (200 мс, лёгкий сдвиг сверху), закрытие (150 мс), плавная смена
цвета индикаторов (220 мс), подсветка при наведении (140 мс). Поддержан
`REDUCED_MOTION` (переменная окружения `EVRIKA_REDUCED_MOTION=1` или ключ
`reduced_motion` в настройках панели): движения отключаются. Отложенные
вызовы отменяются при закрытии окна — «invalid command name» в stderr не
появляется.

## 17. Этап 3 — компактная шапка и контекстная панель

Запрос: индикаторы в шапке перегружали собой (название + цветная точка +
подпись + кнопка «Управление»), а одна большая панель показывала сразу три
секции, из-за чего диагностика одного компонента терялась среди чужих.

### Что сделано

**Компактные индикаторы.** `app/ui/header.py`: индикатор — это цветная
Filled-иконка (19 px) и краткая подпись состояния (12 px). Названий
компонентов, отдельных цветных точек, постоянных обводок и кнопки
«Управление» больше нет: цвет иконки — это и есть состояние компонента,
а рядом стоит текст (цвет всегда дополнен текстом). Высота интерактивной
области 37 px, радиус активной поверхности 9 px, hover — мягкая смена фона
(`CARD`), активный индикатор — `CARD_ALT`.

**Подсказки.** `app/ui/widgets.py` — `Tooltip`: подсказка рисуется меткой в
том же окне (без второго окна Tk) и обновляется вместе с состоянием:
«ANPR-сервис: Работает», «Камера: Нет связи», «Telegram: Проверка».

**Одна панель, три режима.** `app/ui/service_panel.py`: одна физическая
панель (420 px, радиус 12 px, внутренние отступы 18 px) с режимами
`service | camera | telegram`. Нажатие на индикатор открывает панель в его
режиме, нажатие на другой индикатор переключает содержимое без закрытия
панели, повторное нажатие на активный — закрывает. Escape, клик вне панели
и смена раздела приложения закрывают её, как и раньше. Панель не сдвигает
Dashboard, положение и ширина одинаковы во всех режимах, меняется только
содержимое и высота.

**Диагностика по режимам (без дублирования).**
- Сервис: PID, время работы, порт, последняя проверка, последняя ошибка.
  Плюс управление: работает — «Журнал», «Перезапустить», «Остановить»;
  остановлен — «Журнал», «Запустить»; переходное состояние — полоска
  выполнения и заблокированные кнопки; ошибка — текст ошибки и действие
  восстановления, выбранное по фактическому состоянию процесса.
- Камера: название, IP-адрес, приём ANPR-событий, последнее событие.
  Управление ANPR-сервисом в этом режиме нет. При обрыве связи иконка
  красная, а последние известные данные помечаются «(устарело)».
- Telegram: соединение, последняя связь, последняя доставка (+ ошибка
  связи, если она есть). Приём событий и работоспособность RTSP больше не
  смешиваются: `camera_events_view()` в `app/ui/status.py` отвечает на
  вопрос о событиях отдельно от состояния камеры.

**Ошибки, найденные при переработке.**
- `motion.animate_color()` останавливался на доли процента раньше цели:
  последний кадр не применялся, и цвет не совпадал с целевым. Исправлено.
- `focusable()` вешал обработчики фокуса на внутренний холст
  CustomTkinter, где события фокуса не возникают: рамка фокуса не
  показывалась, а Enter/пробел не работали. Теперь клавиатура и фокус
  привязаны к самому виджету (`widgets.bind_widget`).
- Пустой контейнер CustomTkinter занимает 200×200 px: пустые блоки в
  панели растягивали её, а ширина определялась содержимым, а не константой.
  Теперь размеры панели задаются явно, раскладка — через `grid`.
- Положение панели считалось по номинальной ширине: при 125 % DPI панель
  выходила бы за правый край окна. Теперь берётся фактическая ширина.

**Анимации.** Открытие панели — 200 мс (лёгкий сдвиг сверху), закрытие —
150 мс, переключение режима — 140 мс (содержимое выезжает на 10 px, сама
панель не пересоздаётся и не меняет положение), смена цвета иконки — кадрами
(`icons.blend_frames`, без пересоздания картинок на каждый опрос).
`REDUCED_MOTION` сохранён: цвета меняются сразу, анимаций нет.

## 18. Оптимизация отзывчивости интерфейса (21.11)

Консилиум из четырёх независимых проверок (главный поток Tk, опрос данных,
замеры живой системы, история UI-правок) сошёлся на четырёх механизмах
фоновой задержки. Пятый шаг добавлен по результатам замеров.

- **График** перерисовывается только при изменении `hours` (`dashboard.py`).
- **Скрытая панель** больше не делает дорогую перекладку Tk и `update_idletasks()`;
  состояние кнопок при этом обновляется всегда (иначе ломалась блокировка
  кнопок во время операции).
- **Видео:** интервал опроса 40 → 50 мс (соответствует 20 fps), размеры областей
  кэшируются по `<Configure>`, повторный LANCZOS пропускается, если кадр уже
  приведён к нужному размеру.
- **Лента:** карточки переиспользуются по позиции вместо `destroy()`,
  `CTkImage` кэшируется по `event_id`; при смене проезда фото/команда сбрасываются,
  чтобы карточка не показала чужой снимок.
- **`load_dashboard`:** агрегаты (`total`, `unique`, `hours`, `directions`)
  считаются SQL-запросами по всему периоду, `recent` выбирается с `LIMIT
  visible_count + 30`; поиск применяется до лимита. `NOT INDEXED` на трёх
  запросах: на диапазоне дней индекс `(day, captured_at)` вызывает случайные
  чтения и замедляет скан ~в 7 раз.
- **Замер (60 000 строк, 30 дней):** `load_dashboard` 258 мс → 78 мс (~3,3×);
  со включённым поиском 123 мс. Повторный декод 30 JPEG в ленте (~241 мс по
  оценке консилиума) устранён кэшем.
- **Хвосты оптимизации:** `header.set_state()` больше не вызывает
  `update_idletasks()` и не затирает накопленный максимум ширины; запуск
  health-опроса защищён флагом `inflight` — параллельных опросов нет.
- **Ресайз:** перерисовка графика, запоминание геометрии окна и подгонка
  подложки вкладок сведены к одному `after_idle` на пакет `<Configure>`;
  `_fit()` панели пропускает `place_configure()` при неизменных координатах.
- **Кэш агрегатов:** для закрытого периода (`end_day < today`) `total/unique/
  hours/directions` считаются один раз и переиспользуются; инвалидация — по
  `MAX(id)` (новые строки, в том числе backfill) и TTL 300 с. Сегодняшний день
  не кэшируется. Замер на 90 днях / 45 000 строк: 62 → 8 мс, с поиском
  96 → 37 мс.
- **Тесты:** 440 (было 418) — 22 новых проверки на перерисовку графика,
  пропуск перекладки скрытой панели, кэш видео/фото, переиспользование карточек,
  агрегаты с лимитом, отсутствие idle-flush в `set_state`, один одновременно
  работающий health-опрос, дебаунс обработчиков `<Configure>` и кэш агрегатов
  закрытого периода. Полный прогон зелёный.
- Живой сервис во время проверки был остановлен штатно в 22:51, поэтому
  профилирование живого процесса не проводилось; все выводы — по коду и изолированным
  замерам.
